# Progressive disclosure, on-demand skill loading, and context engineering for LLM agents (with multi-product policy separation)

Research date: 2026-10-11. Scope: methods for loading policy/instructions on demand instead of all at once, mapped to the eight problems with the ~800-line / ~25k-token monolithic patient-coordinator prompt. Problem numbers used throughout: (1) attention waste, (2) no rule-level attribution of bad replies, (3) adding a second product line, (4) subtasks have nowhere to go, (5) full prompt cost every message, (6) editing one policy changes unrelated replies, (7) conflicting rules with no record of which won, (8) cannot test one behavior alone. Effort estimates are my own for a one-developer, ~10-hour, TypeScript, hosted Claude Haiku-class build; they are inferences, not sourced.

## Method cards: every credible approach to on-demand policy loading

### Takeaway
Twelve distinct patterns show up across Anthropic, LangChain, Manus, Cursor/Codex docs and the support-automation vendors. They fall into three families: (a) split the prompt into modules and let the model pick (Agent Skills, Fin Procedures), (b) split the prompt into modules and let code pick (path/glob rules, intent routing, state machines), and (c) reduce what is loaded at all (lean base prompt, deferred tools, sub-agents, caching). The strongest-evidenced numbers are for family (c): 65% base-token cut at equal quality (Deep Agents v0.7), 85% token cut plus +25 pts accuracy from deferring tool definitions (Anthropic), 90.2% research-eval gain from sub-agent isolation (Anthropic). Family (a) has no published token or accuracy numbers from Anthropic; the evidence is the architecture description plus authoring limits.

### Cited Findings (the cards)

---
**Card 1 — Agent Skills / SKILL.md progressive disclosure (model picks the module)**
- One line: Pre-load only a one-line name+description per module; the model reads the full module file when it judges it relevant; deeper reference files load only if the module points to them.
- Sources: [Anthropic engineering, "Equipping agents for the real world with Agent Skills"](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) (2025-10-16, updated 2025-12-18 as an open standard; vendor engineering post); [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) (Anthropic docs, undated, live 2026-10); [Claude Code skills docs](https://code.claude.com/docs/en/skills) (Anthropic docs, live 2026-10).
- Claims: "At startup, the agent pre-loads the `name` and `description` of every installed skill into its system prompt"; Claude then "loads the full SKILL.md by reading it" if relevant, and bundled files are read "only as needed," so "the amount of context that can be bundled into a skill is effectively unbounded" — [Anthropic engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills). The description "is critical for skill selection: Claude uses it to choose the right Skill from potentially 100+ available Skills" — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices). "Pattern 2: Domain-specific organization" explicitly recommends organizing content by domain so that "when a user asks about sales metrics, Claude only needs to read sales-related schemas, not finance or marketing data" — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices). "Once a skill loads, its content stays in context across turns, so every line is a recurring token cost" — [Claude Code skills](https://code.claude.com/docs/en/skills). Building a skill "is like putting together an onboarding guide for a new hire" — [Anthropic engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills).
- Problems addressed: 1, 3, 5, 6, 8 (partly 2 via logging which skill was loaded).
- Reported numbers: none reported for token savings or accuracy by Anthropic. Authoring limits only: `name` ≤ 64 chars; `description` ≤ 1,024 chars; "Keep SKILL.md body under 500 lines"; Claude Code truncates description+when_to_use at 1,536 chars in the listing; after compaction Claude Code re-attaches the first 5,000 tokens of each invoked skill under a combined 25,000-token budget — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), [Claude Code skills](https://code.claude.com/docs/en/skills). Third-party audit of Anthropic's 17 official skills: SKILL.md line counts 32–404 (docx 590); 11 of 17 are a single file — [web-developpeur.com](https://www.web-developpeur.com/en/blog/skills-claude-code-patterns-officiels) (2026-06-14, practitioner blog).
- Effort in our setup: ~3–4 h. Build: split the 800 lines into ~8–12 markdown modules (pricing, clinics, packages, payment, photos, scheduling, escalation, tone...) each with a ≤1,024-char third-person description; a core system prompt carrying the catalog of descriptions; a `load_policy(name)` tool whose result is the module body; log every load with the message id.
- Risks: under-triggering ("Claude under-triggers skills far more than it over-triggers them" — [web-developpeur.com](https://www.web-developpeur.com/en/blog/skills-claude-code-patterns-officiels), practitioner claim); extra round-trip per load (latency on SMS); a loaded module stays in context for the rest of the thread; no built-in conflict resolution between modules.
- Verdict: **try first** — it is the direct answer to problems 1/3/5/6/8 and Anthropic's own authoring limits give a concrete spec, but pair it with Card 2 so that the obvious cases (product line, conversation stage) are code-decided and only ambiguous cases are model-decided.

**Card 2 — Code-scoped rule files (glob/path/state-matched rules; code picks the module)**
- One line: Rules carry a machine-checkable scope (file glob, directory, or in our case conversation state/product line) and code injects them only when the scope matches; the model never sees the rest.
- Sources: [Cursor rules docs](https://cursor.com/docs/context/rules) (live 2026-10, vendor docs); [Claude Code memory docs — `.claude/rules/` with `paths:`](https://code.claude.com/docs/en/memory) (live 2026-10, vendor docs); [OpenAI Codex AGENTS.md guide](https://learn.chatgpt.com/docs/agent-configuration/agents-md) (live 2026-10, vendor docs).
- Claims: Cursor has four rule types; with `alwaysApply: false` and `globs` provided the rule is "Auto-attached when a matching file is in context"; with a `description` and no globs the "Agent reads the description and pulls the rule in when relevant" — [Cursor](https://cursor.com/docs/context/rules). Claude Code `.claude/rules/` files can be "scoped to specific file paths, so they only load into context when Claude works with matching files, reducing noise and saving context space," and CLAUDE.md in subdirectories "load on demand" when Claude reads a file there — [Claude Code memory](https://code.claude.com/docs/en/memory). Codex concatenates AGENTS.md "from root down," "Files closer to your current directory override earlier guidance," includes "at most one file per directory," and advises "split instructions across nested directories when you hit the cap" — [Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md).
- Problems addressed: 1, 3, 5, 6, 7 (precedence is explicit), 8.
- Reported numbers: Cursor "Keep rules under 500 lines"; Claude Code "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence"; Codex `project_doc_max_bytes` default 32 KiB — [Cursor](https://cursor.com/docs/context/rules), [Claude Code memory](https://code.claude.com/docs/en/memory), [Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md). No accuracy or token-savings numbers reported.
- Effort in our setup: ~2–3 h. Build: a `policy/` folder where each module has frontmatter `{ product: ["hair"], stage: ["pricing","scheduling"], intent: [...] }`; a TypeScript assembler that reads conversation state (product line, stage, last tool result) and concatenates core + matching modules in a fixed order; a log line listing which modules were included for each reply.
- Risks: scope signals must exist in code (we need an intent/stage field per message); mis-scoped rules silently never load (Claude Code: "A CLAUDE.md in a subdirectory ... doesn't appear under Memory files, because it loads on demand" — [memory docs](https://code.claude.com/docs/en/memory)); contradictory rules still possible ("if two instructions contradict each other, Claude may pick one arbitrarily" — same source).
- Verdict: **try first** — deterministic, cheapest to log and test, and the ordering rule (core first, more specific later) gives problem 7 an explicit precedence record.

**Card 3 — Routing workflow: classify the message, then run a specialized prompt + tool subset**
- One line: A cheap classifier (LLM or rules) labels the inbound message and code dispatches to a per-category prompt and tool allowlist.
- Sources: [Anthropic, "Building effective agents"](https://www.anthropic.com/research/building-effective-agents) (2024-12-19, vendor research post); [Kore.ai, "Design a supervisor routing agent"](https://docs.kore.ai/agent-platform/abl/howto/design-supervisor-routing-agent) (live 2026-10, vendor docs).
- Claims: "Routing classifies an input and directs it to a specialized followup task"; it is a "separation of concerns" that "allows for more specialized prompts" because "optimizing for one kind of input can hurt performance on other inputs"; the example is "directing different types of customer service queries (general questions, refund requests, technical support) into different downstream processes, prompts, and tools"; easy questions can go to Haiku-class models — [Anthropic](https://www.anthropic.com/research/building-effective-agents). Kore.ai: "Make route descriptions mutually exclusive," "If two routes could match the same request, customers may experience inconsistent routing," "Add a route for human help, unsupported requests, or unclear requests," and "Route tests cover success, no-match, ambiguous, and escalation paths" — [Kore.ai](https://docs.kore.ai/agent-platform/abl/howto/design-supervisor-routing-agent).
- Problems addressed: 1, 2 (the route label is the attribution), 3, 5, 6, 7, 8.
- Reported numbers: none reported.
- Effort in our setup: ~3 h (overlaps Card 2). Build: a first Haiku call with a ~10-label intent schema (pricing, clinic-choice, package, payment, photo-upload, scheduling, complaint, human-request, other-product, unclear) returning JSON; the assembler then picks modules and the tool allowlist for that label; "unclear"/"human-request" routes go straight to hand-off.
- Risks: two LLM calls per message (latency/cost); messages that span two intents; classifier drift when new product line added (must add labels). Kore.ai's "mutually exclusive" rule is the mitigation.
- Verdict: **try first** (as the code half of Card 2) — this is the published pattern closest to "patient SMS → the one policy it needs."

**Card 4 — Procedures with "When to use" trigger text and negative examples (support-vendor pattern)**
- One line: Each task-specific procedure carries a short trigger description plus "when to use" and "when NOT to use" examples; the agent evaluates every message against the triggers; global guidance lives separately and is additive.
- Sources: [Intercom, "Building Fin Procedures"](https://www.intercom.com/help/en/articles/13449439) (live 2026-10, vendor help docs); [Fin.ai, "Procedures vs AOPs vs Journeys"](https://fin.ai/learn/ai-agent-procedures-aops-journeys) (2026, vendor comparison — biased); [Decagon, "AOP: the future of CX"](https://decagon.ai/resources/aop-the-future-of-cx) (2025-04-08, vendor post); [Sierra, "Meet Agent Studio"](https://sierra.ai/blog/meet-agent-studio) (2025-09-18, vendor post).
- Claims: Fin's trigger description is limited to 256 characters; Fin "checks each customer message against the trigger description" and a procedure "won't start just because a conversation opened"; good triggers include "inclusion criteria, exclusion criteria, and specific examples"; "When NOT to use" examples are "similar but unrelated queries that should not trigger it, which helps prevent false triggers" — [Intercom](https://www.intercom.com/help/en/articles/13449439). Steps include Instruction, Condition ("IF/ELSE branching for major, mutually exclusive paths"), Run sub-procedure, Handoff to team, End; "Workspace level guidance does not automatically apply inside a Procedure" and guidance is additive ("One doesn't cancel out the other"); Fin's default escalation (asks for a human, strong frustration, repetitive loop) "always applies"; Simulations return Pass/Fail — [Intercom](https://www.intercom.com/help/en/articles/13449439). Decagon: AOPs "combine the power and flexibility of natural language with the precision and rigor of code," "businesses can deploy hundreds of AOPs," with "testing, versioning, and real-time alerts" — [Decagon](https://decagon.ai/resources/aop-the-future-of-cx). Fin.ai characterizes Fin as layered (instructions / deterministic controls / integrations, "Each layer can be edited, tested, and debugged independently"), Decagon as monolithic ("bundles prompts, logic, actions, and rules into a single artifact"), Sierra Journeys as composable visual blocks — [Fin.ai](https://fin.ai/learn/ai-agent-procedures-aops-journeys).
- Problems addressed: 1, 2, 3, 4 (sub-procedures), 6, 7 (explicit "guidance is additive" warning), 8 (per-procedure simulations).
- Reported numbers: trigger text 256 chars; AI-draft input 5,000 chars — [Intercom](https://www.intercom.com/help/en/articles/13449439). Vendor outcome numbers (not about this mechanism specifically): Fin "76% average resolution across 12,000 customers"; Sierra case "75% resolution rate with five customer journeys"; Decagon "80%+ deflection" — [Fin.ai](https://fin.ai/learn/ai-agent-procedures-aops-journeys), [Sierra](https://sierra.ai/blog/meet-agent-studio). All self-reported.
- Effort in our setup: ~1–2 h on top of Card 1/2. Build: for each module add 3–5 "use when" and 3–5 "do NOT use when" example SMS lines to its description; add a mandatory "end / hand off to human" step at the bottom of each module; keep a 10-line always-on guidance block.
- Risks: 256-char triggers are tight for medical nuance; negative examples bloat the catalog; vendors do not publish how ties between two matching procedures are broken (gap).
- Verdict: **try first** — it is the production pattern of three support-automation vendors and maps one-to-one onto "patient SMS → procedure → hand-off."

**Card 5 — Lean base prompt ("right altitude") + evaluation-driven pruning**
- One line: Delete rules the model already follows; keep the base prompt to high-signal tokens and add rules only in response to observed failures.
- Sources: [Anthropic, "Effective context engineering for AI agents"](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) (2025-09-29, vendor engineering post); [LangChain, "Deep Agents v0.7"](https://langchain.com/blog/deep-agents-v0-7) (2026-07-29, vendor release post); [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices).
- Claims: The goal is "the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome"; context "must be treated as a finite resource with diminishing marginal returns"; the "right altitude" avoids both "brittle, hardcoded if-else logic" and vague guidance; "start with a minimal prompt tested on the best available model, then add instructions and examples based on observed failures"; examples should be "a curated set of diverse, canonical cases rather than a long list of edge-case rules" — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents). Deep Agents v0.7 removed its base system prompt, trimmed tool descriptions 43%, and made the todo tool opt-in because "evals showed the planning prompt and write_todos tool did not significantly improve performance" — [LangChain](https://langchain.com/blog/deep-agents-v0-7). Skills guidance: "Default assumption: Claude is already very smart. Only add context Claude doesn't already have"; "Create evaluations BEFORE writing extensive documentation" — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices).
- Problems addressed: 1, 5, 8 (eval set is the by-product).
- Reported numbers: Deep Agents v0.7: "drop base input tokens on a default-agent turn by 65% (~6k → ~2k)" at "comparable performance" ("Reward held steady overall"; reward confidence intervals span zero for every model tested) — [LangChain](https://langchain.com/blog/deep-agents-v0-7). Anthropic: "do the simplest thing that works"; no numbers — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).
- Effort in our setup: ~2 h. Build: a 20-message eval set from real SMS (Anthropic's research team started with "about 20 real-usage queries" — [Anthropic multi-agent post](https://www.anthropic.com/engineering/built-multi-agent-research-system)); run with the full prompt vs. each module deleted; drop any rule whose removal changes nothing.
- Risks: pruning on Haiku may remove rules a weaker model actually needs ("What works perfectly for Opus might need more detail for Haiku" — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)); requires an LLM-judge or hand grading.
- Verdict: **try first** — cheapest win and it produces the eval harness every other card needs.

**Card 6 — Stable cached prefix + append-only module loading (KV-cache / prompt-caching discipline)**
- One line: Keep the shared core (tools + core system prompt) byte-identical and cached; append per-message modules after the cache breakpoint so loading policy on demand does not defeat caching.
- Sources: [Manus, "Context Engineering for AI Agents"](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) (2025-07-18, vendor engineering post by Yichao Ji); [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) (live 2026-10, vendor docs).
- Claims: "the KV-cache hit rate is the single most important metric for a production-stage AI agent"; keep the prompt prefix stable (a per-second timestamp "breaks caching"), keep context append-only, serialize deterministically — [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus). Anthropic: "Cache prefixes are created in the following order: tools, system, then messages"; "Changes at each level invalidate that level and all subsequent levels"; up to 4 cache breakpoints — [Anthropic](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).
- Problems addressed: 5 (directly), 1 (indirectly, by making the loaded set small and the fixed set cheap).
- Reported numbers: Manus input:output ratio ~100:1; cached vs uncached on Claude Sonnet 0.30 vs 3 USD/MTok, "a 10x difference" — [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus). Anthropic: cache reads 0.1x base input price; 5-minute writes 1.25x; 1-hour writes 2x; minimum cacheable prompt 4,096 tokens on Haiku 4.5 but 512 tokens on Haiku 5.5; 5-minute default lifetime refreshed on each use — [Anthropic](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).
- Effort in our setup: ~1 h. Build: order the request as tools → core system block (with `cache_control`) → selected module blocks → messages; never put timestamps or patient-specific data in the core; verify the core exceeds the model's minimum cacheable length (4,096 on Haiku 4.5).
- Risks: on Haiku 4.5 a core under 4,096 tokens is uncacheable, so aggressive pruning (Card 5) can push the core below the threshold; SMS traffic gaps longer than 5 minutes miss the cache unless the 1-hour TTL (2x write cost) is used; changing the tool list per route (Card 3) invalidates the whole cache ("Changing tool definitions invalidates the tools, system, and messages caches" — [Anthropic](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)).
- Verdict: **try first** — one hour, and it decides whether the modular design actually lowers cost or raises it.

**Card 7 — Deferred tool definitions / tool search ("tool loadout")**
- One line: Load only the tool definitions the turn needs, by deferring the rest behind a search tool or by selecting a per-route subset in code.
- Sources: [Anthropic engineering, "Advanced tool use"](https://www.anthropic.com/engineering/advanced-tool-use) (2025-11-24, vendor engineering post); [Drew Breunig, "How to fix your context"](https://www.dbreunig.com/2025/06/26/how-to-fix-your-context.html) (2025-06-26, practitioner blog); [LangChain, "Context engineering for agents"](https://www.langchain.com/blog/context-engineering-for-agents) (2025-07-02, vendor blog).
- Claims: With `defer_loading: true` tools "aren't loaded into Claude's context initially"; the Tool Search Tool "returns references to matching tools, which get expanded into full definitions"; it "doesn't break prompt caching, because deferred tools are added only after Claude searches"; recommended when "tool definitions exceed >10K tokens," with "10+ tools," or with tool-selection errors; "less beneficial with fewer than 10 tools" — [Anthropic](https://www.anthropic.com/engineering/advanced-tool-use). Breunig: above 30 tools "the descriptions of the tools begin to overlap, creating confusion," beyond 100 the model was "virtually guaranteed to fail"; Berkeley Function-Calling Leaderboard shows "every model performs worse when provided with more than one tool" — [Breunig](https://www.dbreunig.com/2025/06/26/how-to-fix-your-context.html) and [his 2025-06-22 post](https://www.dbreunig.com/2025/06/22/how-contexts-fail-and-how-to-fix-them.html).
- Problems addressed: 1, 5 (tool side rather than policy side).
- Reported numbers: ~77K tokens before work begins → ~8.7K with tool search, "an 85% reduction"; MCP-eval accuracy Opus 4 49% → 74%, Opus 4.5 79.5% → 88.1% — [Anthropic](https://www.anthropic.com/engineering/advanced-tool-use). RAG over tool descriptions gave "as much as 3x better tool selection accuracy" (RAG-MCP); dynamic tool selection "improved by 44%" on BFCL and Llama 3.1 8b "fails a benchmark when given 46 tools, but succeeds when given only 19" ("Less is More") — [Breunig](https://www.dbreunig.com/2025/06/26/how-to-fix-your-context.html). Programmatic tool calling cut tokens 37% (43,588 → 27,297) — [Anthropic](https://www.anthropic.com/engineering/advanced-tool-use).
- Effort in our setup: ~1 h (code-side subset per route) or ~1 h to try the `advanced-tool-use-2025-11-20` beta header. Build: a per-route `allowedTools` array (e.g., scheduling route gets calendar + clinic tools only) — note this interacts with Card 6 caching.
- Risks: 14 tools is near the lower bound where Anthropic says benefit is small; per-route tool subsets invalidate the tools-level cache; an extra search step adds latency.
- Verdict: **try if time** — measure our 14 tool definitions' token count first; if under ~10K tokens, keep all tools loaded and rely on Cards 1–3.

**Card 8 — Sub-agents / context quarantine for subtasks**
- One line: Hand a bounded subtask (e.g., compute a package quote, check clinic availability across dates) to a fresh model call with only that subtask's module and tools; return a short structured result to the main thread.
- Sources: [Anthropic, "How we built our multi-agent research system"](https://www.anthropic.com/engineering/built-multi-agent-research-system) (2025-06-13, vendor engineering post); [Anthropic, "Effective context engineering"](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) (2025-09-29); [LangChain, "Deep Agents"](https://www.langchain.com/blog/deep-agents) (2025-07-30, vendor blog); [LangChain deepagents context-engineering docs](https://docs.langchain.com/oss/python/deepagents/context-engineering.md) (live 2026-10); [Claude Code skills docs — `context: fork`](https://code.claude.com/docs/en/skills).
- Claims: "a lead agent coordinates the process" and subagents run "in parallel, each with its own context window," returning condensed findings; each subagent needs "an objective, an output format, tool and source guidance, and clear task boundaries" — [Anthropic multi-agent](https://www.anthropic.com/engineering/built-multi-agent-research-system). Sub-agents "may use tens of thousands of tokens exploring but return condensed summaries of roughly 1,000–2,000 tokens" — [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents). Deepagents: subagents get a fresh context so "the main agent receives only the final result, not the dozens of tool calls that produced it," best practice "return a summary under 500 words" — [LangChain docs](https://docs.langchain.com/oss/python/deepagents/context-engineering.md). Claude Code: a skill with `context: fork` runs with "the system prompt from the agent type" and "the task is the SKILL.md content"; forked skills without an explicit task "return without meaningful output" — [Claude Code skills](https://code.claude.com/docs/en/skills).
- Problems addressed: 4 (directly), 1, 6.
- Reported numbers: Opus 4 lead + Sonnet 4 subagents "outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval"; token usage explained 80% of performance variance; agents use ~4x and multi-agent ~15x the tokens of chat; parallel subagents "cut research time by up to 90%" — [Anthropic multi-agent](https://www.anthropic.com/engineering/built-multi-agent-research-system). Deep Agents blog reports no numbers — [LangChain](https://www.langchain.com/blog/deep-agents).
- Effort in our setup: ~2–3 h. Build: a `runSubtask(moduleName, input)` function that makes one Haiku call with only that module + its tools and returns JSON; expose it to the main agent as a tool; log subtask inputs/outputs.
- Risks: 15x token multiplier is for research, not SMS, but the pattern still doubles calls; lossy hand-back; the 90.2% figure is a research benchmark, not a support benchmark.
- Verdict: **try if time** — only for the 2–3 subtasks that genuinely need many tool calls (quote assembly, multi-date scheduling); do not sub-agent simple replies.

**Card 9 — Deterministic gates outside the prompt (state machine, tool masking, hooks)**
- One line: Enforce hard rules (no price before clinic chosen; no scheduling before deposit) in code that masks or blocks tools, instead of as prompt text that competes with other rules.
- Sources: [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) (2025-07-18); [Claude Code memory docs](https://code.claude.com/docs/en/memory) (live 2026-10); [Intercom Fin Procedures](https://www.intercom.com/help/en/articles/13449439).
- Claims: Manus: "Mask, don't remove" — adding or removing tools mid-task "invalidates the cache and confuses the model"; instead "a context-aware state machine" masks token logits (Auto / Required / Specified modes via response prefill) and tool names share prefixes (`browser_`, `shell_`) so groups can be gated — [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus). Claude Code: instruction files are "context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook" — [memory docs](https://code.claude.com/docs/en/memory). Fin: Condition steps are for "major, mutually exclusive paths"; default escalation triggers "always apply" regardless of procedure — [Intercom](https://www.intercom.com/help/en/articles/13449439).
- Problems addressed: 7 (hard rules cannot conflict with soft ones; the gate log is the record of what won), 6, 8.
- Reported numbers: none reported.
- Effort in our setup: ~2 h. Build: a conversation-state enum per patient (new → qualified → quoted → deposit → scheduled); a `toolPolicy(state)` map using `tool_choice` / allowed-tools; a pre-tool validator that rejects out-of-state calls with an error the model sees; prefix tool names by stage (`quote_*`, `book_*`).
- Risks: state machine drift from real conversations (patients jump stages); over-blocking forces hand-offs.
- Verdict: **try first** for the 3–5 rules that are safety/money-critical; everything else stays as text.

**Card 10 — Per-product knowledge and guidance scoped by audience, shared core defaults to "everyone" (multi-brand pattern)**
- One line: Tag every content item, guidance rule and connector with the product/brand it belongs to; untagged items are shared; a new product is a new tag set, not an edit to existing ones.
- Sources: [Intercom, "Manage multiple brands in Intercom"](https://www.intercom.com/help/en/articles/9744851-manage-multiple-brands-in-intercom) (live 2026-10, vendor help docs); [Codex AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md); [Cursor rules — nested AGENTS.md](https://cursor.com/docs/context/rules).

## Key question 1: Anthropic Agent Skills and the context-engineering post — triggering, testing, versioning, conflicts, token savings

### Takeaway
A skill is triggered by the model, not by code: only `name` + `description` of every skill is pre-loaded into the system prompt, and Claude decides to read the full SKILL.md. Testing is evaluation-first (baseline without the skill, three scenarios, test on Haiku/Sonnet/Opus, measure "did it trigger" separately from "was the output right"); versioning is via version control/plugins only; conflicts are not addressed beyond precedence by scope and namespacing; no token-savings numbers are reported by Anthropic for skills.

### Cited Findings
- Published 2025-10-16; updated 2025-12-18 when Agent Skills were "published as an open standard for cross-platform portability" — [Anthropic engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills).
- Trigger mechanism: "At startup, the agent pre-loads the `name` and `description` of every installed skill into its system prompt"; if Claude judges a skill relevant it loads the full SKILL.md by reading it (in the PDF walkthrough, via a Bash tool); bundled scripts run "at its discretion based on the nature of the task" — [Anthropic engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills).
- Three levels of progressive disclosure: (1) name+description always in the system prompt; (2) SKILL.md body when relevant; (3) bundled files read only as needed, so bundled context is "effectively unbounded" — [Anthropic engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills).
- "Not every token in your Skill has an immediate cost. At startup, only the metadata (name and description) from all Skills is pre-loaded" — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices).
- Description rules: "Always write in third person" because "inconsistent point-of-view can cause discovery problems"; include "both what the Skill does and when to use it"; ≤ 1,024 characters; name ≤ 64 chars lowercase — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices).
- Testing: "Start with evaluation: run agents on representative tasks, find where they struggle, then build skills incrementally"; monitor "unexpected trajectories or overreliance on certain context"; iterate with Claude itself — [Anthropic engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills). "Create evaluations BEFORE writing extensive documentation"; "Build three scenarios"; "Establish baseline: Measure Claude's performance without the Skill"; "There is not currently a built-in way to run these evaluations" — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices).
- Claude Code testing guidance: measure "whether Claude invokes the skill on the right prompts, and whether the output is right when it does"; run prompts "in a fresh session with the skill available and again with it turned off"; `claude plugin eval` runs each prompt with and without the plugin and can gate CI; the `skill-creator` plugin supports `evals/evals.json`, A/B version comparison and description tuning — [Claude Code skills](https://code.claude.com/docs/en/skills).
- Skill-creator's description-tuning procedure (third-party description): 20 queries (8–10 should trigger, 8–10 should not), each run 3 times, a 5-iteration improvement loop, 60/40 train/test split — [web-developpeur.com](https://www.web-developpeur.com/en/blog/skills-claude-code-patterns-officiels) (2026-06-14, practitioner).
- Versioning: "not discussed" in the engineering post; Claude Code docs say skills are shared via "version control (commit `.claude/skills/`), plugins, or managed settings"; `metadata`, `license`, `compatibility` fields are accepted but not acted on — [Anthropic engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills), [Claude Code skills](https://code.claude.com/docs/en/skills).
- Conflict handling: "not addressed" in the engineering post; Claude Code resolves name collisions by scope ("Enterprise over personal, and personal over project") and namespaces plugin skills; it also warns that contradictory instruction files mean "Claude may pick one arbitrarily" and offers `/doctor prompt-audit` to find "files that contradict each other" — [Claude Code skills](https://code.claude.com/docs/en/skills), [Claude Code memory](https://code.claude.com/docs/en/memory).
- Token numbers for skills: none reported in the engineering post ("The page reports no benchmarks, performance metrics, or adoption figures"); only limits: SKILL.md "under 500 lines," listing truncation at 1,536 chars, compaction re-attach 5,000 tokens each / 25,000 combined — [Anthropic engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills), [Claude Code skills](https://code.claude.com/docs/en/skills).
- Context-engineering post (2025-09-29): context engineering is "strategies for curating and maintaining the optimal set of tokens (information) during LLM inference"; "Context, therefore, must be treated as a finite resource with diminishing marginal returns"; "attention budget"; "context rot" from needle-in-a-haystack results; degradation is "a gradient, not a hard cliff"; no accuracy figures given — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).
- System prompt organization: "distinct sections such as background information, instructions, tool guidance, and output description," delineated with XML tags or Markdown headers — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).
- Just-in-time vs pre-loading: agents "keep lightweight identifiers (file paths, queries, links) and load data at runtime with tools"; hybrid — Claude Code "loads CLAUDE.md files up front and uses glob and grep for just-in-time retrieval"; the hybrid "may suit less dynamic domains such as legal or finance" — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).
- Sub-agent numbers: "tens of thousands of tokens" exploring, returning "roughly 1,000–2,000 tokens"; "substantial improvement" over single-agent, no figure — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).

### Inferences
- Because only metadata is pre-loaded, the per-turn fixed cost of a skills catalog for ~12 modules is on the order of 12 × (≤1,024 chars) — roughly 3k tokens worst case, far below the current 25k; the real cost is whichever modules get loaded and then persist across turns.
- Anthropic's own testing recipe (with/without, fresh session, trigger vs output) is directly reusable as our problem-8 harness without any Claude Code dependency.

### Gaps
- No Anthropic-reported token savings or accuracy deltas for skills; "none reported."
- No official guidance on versioning skill content or on resolving two skills whose descriptions overlap.

## Key question 2: Claude Code skills/CLAUDE.md, Cursor rules, Codex AGENTS.md — how rules are scoped to situations

### Takeaway
All three tools combine an always-loaded core file with situation-scoped files, and the scope signal is mostly code-decided: Cursor globs and Claude Code `paths:`/nested CLAUDE.md load on file match, Codex nested AGENTS.md load by directory with nearer files overriding; only Cursor's description-only rules and Claude Code skills are model-decided. All three cap size (200–500 lines or 32 KiB) and state that precedence is by order (more specific last) or by scope rank.

### Cited Findings
- Cursor rule types: Always Apply ("Included in every chat session"); Auto Attached ("Auto-attached when a matching file is in context"); Agent Requested ("Agent reads the description and pulls the rule in when relevant"); Manual ("Included only when you @-mention the rule in chat") — [Cursor](https://cursor.com/docs/context/rules).
- Cursor frontmatter: `alwaysApply: true` → "Always included. Globs and description are ignored"; `globs` provided → auto-attached; `description` only → agent-selected; neither → manual — [Cursor](https://cursor.com/docs/context/rules).
- Cursor size/precedence: "Keep rules under 500 lines"; "Split large rules into multiple, composable rules"; referenced files are not inlined ("The file's contents are not inlined into the prompt"); Team > Project > User and "earlier sources take precedence when guidance conflicts"; nested AGENTS.md "combined with parent directories, with more specific instructions taking precedence" — [Cursor](https://cursor.com/docs/context/rules).
- Claude Code CLAUDE.md: files above the working directory "are loaded at launch. Files in subdirectories load on demand" — once Claude "reads, writes, or edits another file in that subdirectory"; `.claude/rules/*.md` with `paths:` frontmatter "load only when Claude works with matching files"; `@path` imports "don't reduce context, because imported files also load at launch" — [Claude Code memory](https://code.claude.com/docs/en/memory).
- Claude Code guidance on what goes where: "Keep it to facts Claude should hold in every session ... If an entry is a multi-step procedure or only matters for one part of the codebase, move it to a skill or a path-scoped rule" — [Claude Code memory](https://code.claude.com/docs/en/memory). Create a skill when "a section of CLAUDE.md has grown into a procedure rather than a fact" — [Claude Code skills](https://code.claude.com/docs/en/skills).
- Claude Code size: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence"; startup warning when files exceed the recommended length or add up past a combined limit; auto memory loads only "first 200 lines or 25KB" — [Claude Code memory](https://code.claude.com/docs/en/memory).
- Claude Code conflicts/attribution: "if two instructions contradict each other, Claude may pick one arbitrarily"; user rules load before project rules and "Neither set overrides the other"; `/doctor prompt-audit` finds contradictions; the `InstructionsLoaded` hook logs "which CLAUDE.md and rules files are loaded, when they load, and why" — [Claude Code memory](https://code.claude.com/docs/en/memory).
- Claude Code skills invocation controls: `disable-model-invocation: true` removes the description from context and only the user can invoke; `user-invocable: false` lets only Claude invoke; `paths` globs limit auto-activation; nested skills load when Claude reads a file in that subdirectory — [Claude Code skills](https://code.claude.com/docs/en/skills).
- Codex AGENTS.md: global `~/.codex/AGENTS.md` then project root "walks down to the current directory"; "Codex includes at most one file per directory"; files concatenated root-down so "Files closer to your current directory override earlier guidance"; `AGENTS.override.md` replaces a directory's file; `project_doc_max_bytes` default 32 KiB and "stops adding files once the combined size reaches the limit"; advice: "Raise the limit or split instructions across nested directories when you hit the cap"; chain built "once per run" — [Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md).
- Deepagents equivalent: "Unlike skills, memory is always injected" (AGENTS.md), so keep it minimal; skills load frontmatter only at startup — [LangChain docs](https://docs.langchain.com/oss/python/deepagents/context-engineering.md).

### Inferences
- The shared design across all three: one small always-on file (facts, conventions) + scoped files (procedures) + explicit precedence by order. Translating "file path" to "conversation state/product line" gives us Card 2 directly.
- Claude Code's `InstructionsLoaded` hook is the closest published analog to the owners' problem 2 (which rule caused a bad reply): log the set of loaded modules per turn.

### Gaps
- None of the three tools publish adherence or token numbers behind their line limits; the 200/500-line figures are stated without supporting data.

## Key question 3: LangChain Deep Agents — planning tool, sub-agents, filesystem, and context size vs quality

### Takeaway
Deep Agents (2025-07-30) names four ingredients — detailed system prompt, planning/todo tool, sub-agents, filesystem — and frames sub-agents as "context management"; the only measured result is the v0.7 release (2026-07-29): removing the base prompt, trimming tool descriptions 43% and making the todo tool opt-in cut base input tokens 65% (~6k → ~2k) with reward "held steady." - Sub-agent isolation in docs: subagents get a fresh context and "the main agent receives only the final result, not the dozens of tool calls that produced it"; framed as solving "the context bloat problem"; instruct subagents to "return a summary under 500 words" — [LangChain deepagents docs](https://docs.langchain.com/oss/python/deepagents/context-engineering.md).

### Inferences
- The v0.7 result is the cleanest published evidence that a large fixed prompt can be cut by roughly two-thirds without measurable quality loss — the closest analog to our 25k-token monolith.
- The todo/planning tool is not worth building for an SMS bot: the one team that measured it dropped it from the default.

### Gaps
- The Deep Agents blog gives no numbers on context size vs quality; the v0.7 eval suite is not described in enough detail to compare with a support workload.

## Key question 4: Manus "Context Engineering for AI Agents" (2025-07-18) — the specific lessons with numbers

### Takeaway
Six lessons: (1) KV-cache hit rate is "the single most important metric" (100:1 input:output; 10x cached vs uncached cost); (2) mask tools, don't remove them; (3) filesystem as unlimited restorable memory; (4) recite goals via todo.md (~50 tool calls per task); (5) keep failures in context; (6) avoid few-shot pattern lock-in. They rebuilt the framework four times.

### Cited Findings
- Framing: Manus bet on context engineering over fine-tuning so improvements ship "in hours instead of weeks"; "rebuilt its agent framework four times" ("Stochastic Graduate Descent") — [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus).
- KV-cache: "the KV-cache hit rate is the single most important metric for a production-stage AI agent"; average input:output ratio "about 100:1"; Claude Sonnet cached input "0.30 USD/MTok versus 3 USD/MTok uncached, a 10x difference"; keep the prefix stable (a per-second timestamp breaks caching), context append-only, deterministic serialization, explicit cache breakpoints where required — [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus).
- Mask, don't remove: adding/removing tools mid-task "invalidates the cache and confuses the model when earlier turns reference missing tools"; use "a context-aware state machine" and mask token logits; three modes (Auto, Required, Specified) via response prefilling; shared tool-name prefixes (`browser_`, `shell_`) to gate groups — [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus).
- Filesystem as context: windows of "128K tokens or more" are "often insufficient and sometimes a liability" (oversized observations, degradation at length, cost); the filesystem is "unlimited, persistent external memory"; compression must be restorable (drop a page, keep its URL) — [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus).
- Recitation: a typical task "requires about 50 tool calls"; rewriting todo.md "pushes global goals into the model's recent attention, reducing lost-in-the-middle drift" — [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus).
- Keep the wrong stuff in: "Erasing failure removes evidence. And without evidence, the model can't adapt"; error recovery is "a clear sign of true agentic behavior" — [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus).
- Don't get few-shotted: in a batch of 20 resumes the agent "fell into a rhythm and drifted"; fix with controlled variation in serialization and phrasing — [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus).
- Corroborating Anthropic cache pricing: cache reads 0.1x base input, 5-min writes 1.25x, 1-h writes 2x; min cacheable 4,096 tokens on Haiku 4.5, 512 on Haiku 5.5; order tools → system → messages — [Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).

### Inferences
- Lesson 2 argues against Card 3's per-route tool subsets if we also want Card 6's caching; keep all 14 tool definitions constant and gate them by state (Card 9) instead.
- Lesson 1 implies the modular prompt must be assembled in a stable order (core cached, modules appended) or the per-message cost could rise above the monolith's cached cost.

### Gaps
- Manus reports no quality/accuracy numbers for any lesson; all figures are cost or workload statistics.

## Key question 5: Practitioner writeups on context engineering with before/after numbers

### Takeaway

Most other "context engineering" posts are vendor marketing without numbers.

### Cited Findings
- Anthropic tool search: ~55K tokens for 58 tools across five servers; ~77K total before work begins vs "~8.7K tokens, preserving 95% of context window"; "an 85% reduction"; Opus 4 49% → 74%, Opus 4.5 79.5% → 88.1% on MCP evals; Anthropic saw tool definitions "consume 134K tokens before optimization"; programmatic tool calling −37% tokens (43,588 → 27,297), knowledge-retrieval 25.6% → 28.5%, GIA 46.5% → 51.2% — [Anthropic, Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use) (2025-11-24).
- Anthropic multi-agent: "outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval"; token usage explains 80% of variance (95% with tool calls and model choice); ~4x tokens for agents, ~15x for multi-agent vs chat; started with "about 20 real-usage queries"; LLM-as-judge 0.0–1.0 score — [Anthropic](https://www.anthropic.com/engineering/built-multi-agent-research-system) (2025-06-13).
- Wix: context before was "massive nested JSON for meeting history and contact lists"; after pre-filtering/ranking, one line per candidate ("~96% token reduction"), semantic slugs instead of IDs, strict JSON output; "45.8% reduction in average duration"; "Avg cost was reduced by ~23.2X Cheaper"; switched to Gemini Flash 2.0; 150 requests per run; "No accuracy or quality figures are given" — [Wix Engineering](https://www.wix.engineering/post/the-art-behind-better-ai-how-we-achieved-a-46-speed-boost-and-23-cost-reduction) (2025-12-09).
- Breunig failure modes (2025-06-22): Context Poisoning ("a hallucination or other error makes it into the context, where it is repeatedly referenced"), Context Distraction, Context Confusion ("superfluous content in the context is used by the model to generate a low-quality response"), Context Clash; Gemini 2.5 Pokémon degraded "significantly beyond 100k tokens"; BFCL: "every model performs worse when provided with more than one tool"; quantized Llama 3.1 8B failed with 46 tools and "succeeded" with 19; Databricks: "model correctness began to fall around 32k for Llama 3.1 405b"; sharded prompts "an average drop of 39%," o3 "dropped from 98.1 to 64.1" — [Breunig](https://www.dbreunig.com/2025/06/22/how-contexts-fail-and-how-to-fix-them.html).
- Breunig fixes (2025-06-26): six tactics (RAG, tool loadout, context quarantine, pruning, summarization, offloading); RAG-MCP "as much as 3x better tool selection accuracy," overlap above 30 tools, near-certain failure above 100; "Less is More": dynamic selection "improved by 44%" on BFCL with power/speed savings "18% and 77%"; Provence pruning "cutting 95% of the content"; Anthropic "think" tool "up to a 54% improvement"; "context is not free" — [Breunig](https://www.dbreunig.com/2025/06/26/how-to-fix-your-context.html).
- Deep Agents v0.7: −65% base input tokens (~6k → ~2k), reward steady — [LangChain](https://langchain.com/blog/deep-agents-v0-7) (2026-07-29).
- Lower-quality/vendor claims found but not relied on: Pinecone/Nexus "70–95% reduction in token consumption per agent" (vendor case study, no method detail) — [Pinecone](https://www.pinecone.io/blog/introducing-nexus-knowledge-engine/); Blake Crosley "60–70% reduction from system prompt architecture" (blog, no before/after prompt shown) — [blakecrosley.com](https://blakecrosley.com/blog/context-is-the-new-memory).

### Inferences
- Across sources the consistent shape is: large reductions in fixed context (60–96%) with flat-to-better quality when the removed material was redundant, and quality gains (not just savings) when the removed material was confusable (similar tools/rules).
- The owners' problem 1 ("attention wasted") has direct empirical support in the tool-count results: more candidate instructions, worse selection.

### Gaps
- No practitioner writeup found that reports before/after numbers for splitting a customer-support system prompt into on-demand policy modules; the nearest analogs are tool definitions (Anthropic) and base harness prompts (LangChain).

## Key question 6: Model-picks-the-skill vs code-picks-the-skill — tradeoffs and failure modes

### Takeaway
Model-picks (skills, Cursor "Agent Requested," Fin "When to use") handles open-ended phrasing and needs no state machinery, but under-triggers, cannot be exhaustively tested without a trigger eval, and depends on description wording. Code-picks (globs, `paths:`, nested AGENTS.md, routing, state machines) is deterministic, loggable and cacheable, but needs a reliable scope signal and silently never loads a mis-scoped rule. Every mature system documented here uses both: code for the obvious scope (product, directory, state), the model for ambiguous intent, plus a human/unclear fallback route.

### Cited Findings
- Cursor documents both in one table: globs → "Auto-attached when a matching file is in context" (code); description → "Agent reads the description and pulls the rule in when relevant" (model); "The doc does not describe the internal mechanism ... for description-based rules" — [Cursor](https://cursor.com/docs/context/rules).
- Claude Code offers both on the same skill: `paths` globs (code) and description (model), plus `disable-model-invocation` to turn off model selection entirely — [Claude Code skills](https://code.claude.com/docs/en/skills).
- Model-picks failure mode 1 (under-triggering): "Claude under-triggers skills far more than it over-triggers them"; it "only consults a skill for a task it can't handle trivially"; descriptions should be "a little pushy" (e.g., "Use this skill any time a spreadsheet file is the primary input or output") — [web-developpeur.com](https://www.web-developpeur.com/en/blog/skills-claude-code-patterns-officiels) (2026-06-14, practitioner; attributes the point to Anthropic's skill-creator).
- Model-picks failure mode 2 (vocabulary mismatch): a skill "never activates, because its description uses vocabulary that doesn't overlap with how users phrase requests" — [DataCamp exercise](https://campus.datacamp.com/courses/introduction-to-agent-skills/sharing-troubleshooting-skills?ex=6) (practitioner course material).
- Model-picks failure mode 3 (overlap/confusion at scale): above ~30 tools descriptions "begin to overlap, creating confusion" — [Breunig](https://www.dbreunig.com/2025/06/26/how-to-fix-your-context.html); Anthropic's own example of confusable names `notification-send-user` vs `notification-send-channel` — [Anthropic](https://www.anthropic.com/engineering/advanced-tool-use).
- Model-picks mitigation: Fin's "When NOT to use" examples exist specifically "to prevent false triggers from similar but unrelated queries," and Fin evaluates every message so a procedure "won't start just because a conversation opened" — [Intercom](https://www.intercom.com/help/en/articles/13449439); Anthropic's skill-creator tunes descriptions against 20 labeled queries with a 60/40 held-out split — [web-developpeur.com](https://www.web-developpeur.com/en/blog/skills-claude-code-patterns-officiels).
- Model-picks testing requirement: measure "whether Claude invokes the skill on the right prompts" separately from output quality, in fresh sessions because "leftover context from authoring the skill will mask gaps" — [Claude Code skills](https://code.claude.com/docs/en/skills).
- Code-picks failure mode 1 (silent non-load): a subdirectory CLAUDE.md "doesn't appear under Memory files, because it loads on demand"; debug with the `InstructionsLoaded` hook — [Claude Code memory](https://code.claude.com/docs/en/memory).
- Code-picks failure mode 2 (wrong key): Intercom brand matching "using the brand's internal ID — not its display name"; mismatches silently exclude articles from Fin's search — [Intercom brands](https://www.intercom.com/help/en/articles/9744851-manage-multiple-brands-in-intercom).
- Code-picks failure mode 3 (ambiguous routes): "If two routes could match the same request, customers may experience inconsistent routing"; mitigate with mutually exclusive route descriptions and a route for "human help, unsupported requests, or unclear requests" — [Kore.ai](https://docs.kore.ai/agent-platform/abl/howto/design-supervisor-routing-agent).
- Code-picks and caching: changing tool definitions per route invalidates tools/system/messages caches — [Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching); Manus: removing tools mid-task "confuses the model when earlier turns reference missing tools" — [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus).
- Anthropic's routing rationale favors code/classifier selection where categories are "better handled separately" and "classification can be handled accurately" by "an LLM or a more traditional classification model/algorithm" — [Anthropic](https://www.anthropic.com/research/building-effective-agents).
- Hybrid precedent: Claude Code "loads CLAUDE.md files up front and uses glob and grep for just-in-time retrieval" — [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).

### Inferences
- For an SMS bot the scope signals are strong (product line from the number/campaign, stage from the state machine, intent from a one-label classifier), so code-picks should carry most of the load; model-picks via a `load_policy` tool is the right fallback for the "unclear" route and for mixed-intent messages.
- Problem 2 (attribution) is only solvable if the chosen path is logged; code-picks logs for free, model-picks logs only if the load is a tool call rather than a silent file read.

### Gaps
- No source quantifies false-trigger vs missed-trigger rates for model-picked skills on any benchmark.
- No vendor documents how it resolves two procedures whose triggers both match.

## Key question 7: How multi-product companies keep per-product policy separate with a shared core; the standard way to add a second domain

### Takeaway
The documented pattern (Intercom brands/audiences, Codex/Cursor nested AGENTS.md, Anthropic routing, Fin/Sierra/Decagon procedures) is: a shared core that applies to "everyone," product-specific content/guidance/procedures tagged to a product audience and loaded only for that product, more-specific items overriding the shared ones by order, and a router or product field deciding which set is active. Adding a second domain is a new tag/folder/route plus new procedures and tests; the first domain's files are not edited.

### Cited Findings
- Intercom: two approaches — one workspace with up to 300 brands, or fully separate workspaces for "full isolation of support requests, contacts, permissions, and information"; the two can be combined — [Intercom brands](https://www.intercom.com/help/en/articles/9744851-manage-multiple-brands-in-intercom), [Intercom community](https://community.intercom.com/ask-the-intercom-team-about-fin-54/supporting-multiple-products-with-fin-4514).
- Intercom per-brand scoping: "Audiences now control what Fin knows, while Fin identities control how Fin appears over chat and email"; Content, Fin Guidance (tone, rules, policies) and Data Connectors "can each be targeted to an Audience"; untargeted items "will be available to 'Everyone' by default"; Fin uses "only the active brand's Help Center content and unbranded content"; adding a brand is a separate configuration step (New brand → Help Center → sender → Messenger style) — [Intercom brands](https://www.intercom.com/help/en/articles/9744851-manage-multiple-brands-in-intercom).
- Intercom per-product data: staff recommend per-product attribute naming (e.g., `productA_attribute`) and boolean flags for which products a user has — [Intercom community](https://community.intercom.com/helpdesk-9/setting-up-intercom-for-multiple-products-4716) (community thread, 2023-era).
- Fin: workspace-level guidance "does not automatically apply inside a Procedure" and must be selected; custom guidance "applies only to the procedure you write it in"; guidance is additive; sub-procedures "are local and can't be called by unrelated procedures"; Agentic Switch lets Fin move to another live procedure "if the customer's intent changes" — [Intercom Fin Procedures](https://www.intercom.com/help/en/articles/13449439).
- Fin/Decagon/Sierra testing as the regression guard when adding a domain: Fin "central simulation library supports regression testing when any Procedure, policy, or knowledge article changes"; Decagon "unit tests, regression tests that replay historical transcripts, AI-simulated personas, live A/B testing, and Agent Versioning with rollback"; Sierra "version-controlled snapshots, a staging-to-production pipeline, and instant rollback" — [Fin.ai comparison](https://fin.ai/learn/ai-agent-procedures-aops-journeys) (vendor-authored, 2026).
- Sierra organization: knowledge (help centers, documents, custom JSON articles), journeys (natural-language workflows, "tailored per channel"), brand/persona; "Before releases, you can run simulations"; one retailer reached "75% resolution rate with five customer journeys" — [Sierra](https://sierra.ai/blog/meet-agent-studio) (2025-09-18).
- Decagon: "businesses can deploy hundreds of AOPs"; "you always know why an AI agent made a particular decision at any point in time" (claim, no mechanism) — [Decagon](https://decagon.ai/resources/aop-the-future-of-cx) (2025-04-08).
- Anthropic routing: customer-service queries "directed into different downstream processes, prompts, and tools" because "optimizing for one kind of input can hurt performance on other inputs" — [Anthropic](https://www.anthropic.com/research/building-effective-agents) (2024-12-19).
- Coding-tool analog: "Repo-wide rules go in the root AGENTS.md; service-specific rules go in nested files"; nearer files override — [Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md); nested AGENTS.md "combined with parent directories, with more specific instructions taking precedence" — [Cursor](https://cursor.com/docs/context/rules).
- Skills analog: "Pattern 2: Domain-specific organization ... organize content by domain to avoid loading irrelevant context" with `reference/finance.md`, `reference/sales.md` etc. — [best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices).
- Supervisor/specialist pattern (practitioner sources, lower authority): each specialist has "its own system prompt focused on its domain, a tool set scoped to its tasks, and a knowledge base subset"; "when your returns policy changes, you update the returns agent's system prompt" — [claudeimplementation.com tutorial](https://claudeimplementation.com/blog/claude-multi-agent-customer-support-tutorial), [SimbaVoice](https://simbavoice.ai/resources/multi-agent-architectures-for-customer-service); Kore.ai: "Make route descriptions mutually exclusive" and add a fallback route — [Kore.ai](https://docs.kore.ai/agent-platform/abl/howto/design-supervisor-routing-agent).
- Telco/bank-specific engineering writeups: none found that describe per-product policy organization with numbers (searches returned job ads and generic vendor pages).

### Inferences
- Our concrete mapping: `policy/shared/` (identity, tone, escalation triggers, payment-security rules) + `policy/hair/` + later `policy/fertility/`; a `product` field on the conversation selects the folder; shared loads first, product modules after (override by order); hand-off and "unclear" routes are shared. Fertility becomes a new folder, a new router label, and a new eval set; `policy/hair/` is untouched.
- Fin's warning that workspace guidance does not auto-apply inside a procedure is a design choice worth copying explicitly: decide per module whether the shared block is injected, and log it.

### Gaps
- No engineering blog from Intercom, Zendesk, Ada, Decagon or Sierra describes the internal prompt/knowledge architecture for multi-product tenants with numbers; only help-center configuration pages and marketing comparisons were found.
- No source on how a telco or bank support bot organizes per-product policy was found.

## Summary: direct answers to each key question

### Takeaway
(Q1) Skills are model-triggered from a pre-loaded name+description; testing is with/without evals in fresh sessions measuring trigger and output separately; versioning is left to git/plugins; conflicts are handled only by scope precedence and an audit command; Anthropic reports no token-savings numbers for skills ([Anthropic engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills), [Claude Code skills](https://code.claude.com/docs/en/skills)). (Q2) Claude Code, Cursor and Codex scope rules by file path/glob/directory (code-decided) with an always-on core, caps of 200–500 lines or 32 KiB, and "more specific last/overrides" precedence; only description-only rules and skills are model-decided ([Cursor](https://cursor.com/docs/context/rules), [Claude Code memory](https://code.claude.com/docs/en/memory), [Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md)). (Q3) Deep Agents' four ingredients are prompt, planning tool, sub-agents, filesystem; the blog reports no size-vs-quality numbers, but v0.7 cut base tokens 65% at equal reward and dropped the planning tool from the default ([LangChain](https://www.langchain.com/blog/deep-agents), [v0.7](https://langchain.com/blog/deep-agents-v0-7)). (Q4) Manus: KV-cache hit rate first (100:1, 10x), mask don't remove, filesystem as memory, todo recitation (~50 calls/task), keep failures, avoid few-shot lock-in ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)). (Q5) Credible before/after numbers: −85% tokens/+25 pts (Anthropic tool search), −65% at equal quality (Deep Agents), −96% context/−45.8% latency/23.2x cost (Wix), 19-vs-46 tools pass/fail and +44% (Breunig's compiled papers). (Q6) Model-picks is flexible but under-triggers and is hard to attribute; code-picks is deterministic and loggable but needs a scope signal; use code for product/stage/intent, the model for ambiguous cases, always with a human/unclear fallback. (Q7) Multi-product support is organized as shared-core-for-everyone plus product-tagged content/guidance/procedures loaded only for that product, selected by a product field or router, with per-product simulations as the regression guard; a second domain is a new tag/folder/route, not an edit to the first ([Intercom brands](https://www.intercom.com/help/en/articles/9744851-manage-multiple-brands-in-intercom), [Fin Procedures](https://www.intercom.com/help/en/articles/13449439), [Anthropic routing](https://www.anthropic.com/research/building-effective-agents)).
