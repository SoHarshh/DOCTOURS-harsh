Research report: turning one giant LLM prompt into a routed, testable, escalating system

Topic slug: llm-routing-monolith · Swarm supervisor report · 2026-10-11 (America/New_York) · For Rudraksh Awasthi

Executive summary

  • Bottom line. The evidence supports the rebuild with three corrections. Code, not the model, picks which policy modules load. Precedence and escalation live in code. Loaded text goes after a cached prefix that stays above the model's cache minimum.
  • What failed in head-to-heads. Model-triggered skills lost every comparison we found. Vercel's skill was never invoked in 56% of cases, and LangChain reached only 70% invocation even when prompted. Prompt-level rule precedence holds only about 40-48% of the time under conflict.
  • What to build in the 10 hours (section 3). A promptfoo harness run 3+ times per method. A small always-on core plus up to 3 code-picked modules per turn. A regex-then-Haiku router that fails open. Escalation as a code-executed tool with a receipt check. Grounding validators with one retry. A cache layout that puts skill text after the prefix.
  • Biggest risk to the plan. On Claude Haiku 4.5 a prompt shorter than 4,096 tokens is not cached at all, so a cached monolith could be cheaper per turn than an uncached routed build. Measure both.
  • Biggest unlisted fix. "Pretend" handoffs and completions cause 45-48% of failures in tau2-bench single-control domains. A cheap code check against actual tool calls catches them, and LLM judges do not.
  • Scope. 77 method cards across families A-K (A 4, B 7, C 4, D 6, E 5, F 10, G 11, H 10, I 7, J 7, K 6): 31 try first, 22 try if time, 24 skip. The numbers table has 262 rows. Every card cites opened sources with dates.

Family A: Progressive disclosure / skill loading

TRY IF TIME A1. Model-picked skills (SKILL.md progressive disclosure)
Only each skill's name and description sit in context. The model decides when to load the full body.
  • Sources:
  • Anthropic Engineering, "Equipping agents for the real world with Agent Skills" (2025-10-16, blog) https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills
  • Skill authoring best practices (undated, docs) https://docs.claude.com/en/docs/agents-and-tools/agent-skills/best-practices
  • Workday, "Report: Progressive Disclosure of Agent Skills" (2026-09-28, paper) https://arxiv.org/abs/2609.35692
  • LangChain "Evaluating Skills" (2026-03-05, blog) https://blog.langchain.com/evaluating-skills/
  • Claims: Skills are folders whose metadata (name ≤64 chars, description ≤1,024 chars) is always present. The body (under 500 lines) and any linked files load only when the model judges them relevant. Workday measures large token savings over eager loading and better skill retrieval as the library grows, at a small latency cost. The weak point is triggering: LangChain found Claude Code never invoked a relevant skill on one task, and prompting only raised invocation to 70%.
  • Problems (1-8, Esc): 1, 3, 5, 6 (partly), 8 (per-skill evals). Esc: no.
  • Reported numbers: "up to 81.7% of tokens originally used in the eager loading regime"; "a 15% increase in the agent's overall latency (from 1.75 to 2.01 seconds)" (Workday). "Even including a prompt to invoke skills only brought invocation rate up to 70%" (LangChain).
  • Effort: about 3 h. Build a TS skills/ directory of markdown modules with frontmatter, plus a load_skill(name) tool for Haiku. The system prompt lists names and descriptions.
  • Risks: missed invocation (see A3, where Vercel saw 56% never invoked). It adds an extra round trip per load, which hurts SMS latency. A wrong skill can be loaded silently.
  • Verdict: TRY IF TIME Use the skill format for packaging, but don't let a Haiku-class model decide whether a policy applies (see A2).
  • Scores: Ev 4 · Cr 4 · Cost 4 · Rel 4 · Rec 5
  • Cross-refs: A2, A3 (stronger alternatives); J2 (single agent with skills); K2 (manifest schema).
TRY FIRST A2. Code-picked skills / scoped rules (deterministic loading)
Code (route label, conversation state, file glob) decides which policy modules enter the prompt, not the model.
  • Sources:
  • Cursor Rules docs (undated, docs) https://cursor.com/docs/context/rules
  • Claude Code memory docs (undated, docs) https://code.claude.com/docs/en/memory
  • "How Well Do Agentic Skills Work in the Wild" (2026-04-06, paper) https://arxiv.org/abs/2604.04323
  • Fin, "How Fin Scales Customer-Defined Behaviour" (2026-09-25, blog) https://fin.ai/research/how-fin-scales-customer-defined-behaviour
  • Claims: Cursor and Claude Code both scope rules by path or glob, so rules attach automatically and not at the model's discretion. In Skills in the Wild, force-loading the right skills beat agent-decided loading, and distractor skills cut the score further. Fin runs a selector per behaviour surface (guidance, connectors, procedures), each with its own contract. Selectors fail open: the full set passes on error or timeout. A/B tests against the full prompt kept resolution stable while cost and latency fell. Fin's selectors are vendor fine-tuned cross-encoders. We would copy the contract (fail-open, per-surface gating, absolute relevance bar) but implement the selection with a router label or a prompted Haiku call.
  • Problems (1-8, Esc): 1, 2 (we know which modules were loaded), 3, 5, 6, 8. Esc: indirectly (escalation module always on).
  • Reported numbers: forced load 55.4% vs agent-decided curated 51.2% vs +distractors 43.5% (Claude Opus 4.6); "only 49% of Claude trajectories load all curated skills ... falling to 31% with distractors" (Skills in the Wild). "61% of planning calls came back with an empty plan"; "84% of procedure relevance checks find nothing that applies" (Fin).
  • Effort: about 3 h. Build a TS map route → [policyModuleIds] that assembles the prompt from markdown modules, logs the module IDs per turn, and falls back to the full set if the route is unknown.
  • Risks: the router becomes the single point of failure (see B7). Coarse routes over-load modules. Fin's numbers come from fine-tuned selectors and don't transfer directly.
  • Verdict: TRY FIRST It is the cheapest way to fix 1/5/6 with a per-turn record of what was loaded.
  • Scores: Ev 4 · Cr 4 · Cost 5 · Rel 5 · Rec 5
  • Cross-refs: A3, A7, B4, B7, K1, K2. Fin selectors are fine-tuned; we copy the contract only.

  • Risks: these are coding-agent evals, not support bots. Frontier models handle a trimmed prompt better than Haiku may.

TRY FIRST A7. Few, compact, curated skills (anti-conflict curation)
Keep the module count per turn small, modules compact, and human-written. Avoid overlap.
  • Sources:
  • SkillsBench (2026-02-13, v4 2026-06-14, paper) https://arxiv.org/abs/2602.12670
  • Skills in the Wild (2026-04-06, paper) https://arxiv.org/abs/2604.04323
  • LangChain "LangChain Skills" (2026-03-04, blog) https://blog.langchain.com/langchain-skills/
  • Claims: Curated skills help a lot on average, but gains peak at 2-3 skills per task and fall at 4 or more. Compact skills beat comprehensive docs, and self-generated skills hurt. Distractor skills reduce performance in the wild. LangChain saw a large jump from well-built domain skills.
  • Problems (1-8, Esc): 1, 6, 7 (fewer overlapping modules means fewer conflicts). Esc: no.
  • Reported numbers: "33.9% to 50.5% (+16.6 percentage points)"; "one Skill gain +18.0 pp, 2–3 Skills gain +19.0 pp, and ≥4 Skills give only +10.1 pp" (SkillsBench). "from 29% to 95%" (LangChain; the worker snippet said 25%, but the source says 29%).
  • Effort: 0 h extra. It is a design rule: cap modules per route at 3 and lint for overlap.
  • Risks: coding/agentic benchmarks, not support.
  • Verdict: TRY FIRST as a design constraint on A2.
  • Scores: Ev 4 · Cr 4 · Cost 5 · Rel 4 · Rec 5
  • Cross-refs: J2 (confusability), I4 (instruction budget), K2.

Family B: Routing the message to the right rules

TRY FIRST B1. Deterministic rules/regex router
Keyword, regex or data-attribute rules route obvious cases (asks for a human, STOP, "ok thanks") before any model call.
  • Sources:
  • Intercom, "Manage Fin AI Agent's escalation guidance and rules" (undated, docs) https://www.intercom.com/help/en/articles/12396892
  • Fin, "To escalate or not to escalate" (2025-09-11, blog) https://fin.ai/research/to-escalate-or-not-to-escalate-that-is-the-question/
  • Claims: Intercom separates deterministic Escalation Rules (data attributes) from natural-language Guidance. Default triggers include an explicit request for a human, strong frustration and a repetitive loop. Fin layered hard guardrails on its LLM decision, such as never offering escalation twice in a row and not escalating on the first message unless a guideline allows it.
  • Problems (1-8, Esc): 5 (no model for trivial turns), 2, 8 (rules unit-testable). Esc: yes.
  • Reported numbers: none reported for rules alone.
  • Effort: about 1 h. Build a TS preRoute(msg) with a regex table (human/person/agent/call me, ack-only messages), each rule with an ID.
  • Risks: brittle to paraphrase and multilingual SMS. False positives on "agent" in other senses.
  • Verdict: TRY FIRST as stage 1 of B4.
  • Scores: Ev 2 · Cr 4 · Cost 5 · Rel 5 · Rec 4
  • Cross-refs: B4, E2 (shared regex for "talk to a person").
TRY IF TIME B2. Embedding (semantic) router
Embed the message, take the nearest labelled examples or centroids, and route above a similarity threshold.
  • Sources:
  • aurelio-labs/semantic-router (repo created 2023-10-30, last push 2026-09-29) https://github.com/aurelio-labs/semantic-router
  • "Beyond the Hype: Embeddings vs. Prompting for Multiclass Classification" (2025-04-05, v3 2025-11-11, paper) https://arxiv.org/abs/2504.04277
  • Claude ticket-routing guide (undated, docs) https://docs.claude.com/en/docs/about-claude/use-case-guides/ticket-routing
  • Claims: Semantic routing replaces an LLM call with a vector similarity lookup. On Thumbtack's labelled data, an embeddings classifier beat prompting on accuracy, speed and cost. Anthropic's guide reports retrieved similar examples raising routing accuracy.
  • Problems (1-8, Esc): 5, 3 (adding a product line = adding examples), 8. Esc: partly.
  • Reported numbers: "the embeddings approach has 49.5% higher accuracy than the prompting approach"; "14 and 81 times faster"; "up to 10 times cheaper" (Thumbtack). "from 71% accuracy to 93% accuracy" (Anthropic guide, measured; its other percentages are TARGETS).
  • Effort: about 3 h. Build a TS embedding call (hosted embeddings API), 10-20 examples per route, cosine top-k, and a threshold.
  • Risks: needs labelled examples. Thresholds need tuning. Thumbtack trained a classifier on embeddings (light, not LLM fine-tuning).
  • Verdict: TRY IF TIME Use it as the cheap middle stage if Haiku routing latency hurts.
  • Scores: Ev 3 · Cr 3 · Cost 3 · Rel 4 · Rec 4
TRY FIRST B3. Small-LLM (prompted Haiku) classifier router
One cheap structured-output Haiku call labels the intent/route, optionally with retrieved examples.
  • Sources:
  • Claude ticket-routing guide (undated, docs) https://docs.claude.com/en/docs/about-claude/use-case-guides/ticket-routing
  • Arch-Router paper, Table 1 (2025-06-19, paper) https://arxiv.org/html/2506.16655
  • "Intent Detection in the Age of LLMs" (2024-10-02, paper) https://arxiv.org/abs/2410.01627
  • Claims: Anthropic documents LLM ticket routing with few-shot and retrieved examples. In Arch-Router's benchmark a prompted Claude-haiku-3.5 routed at 84.96% overall vs 92.79% for Sonnet 3.7 and 93.17% for the trained Arch-Router. Arora et al. find LLM intent detection accurate but slow, which motivates hybrids.
  • Problems (1-8, Esc): 1, 3, 5 (partly), 8. Esc: yes (an "escalate" label).
  • Reported numbers: "Claude-haiku-3.5 88.21 81.46 83.72 84.96" (turn/span/conversation/overall, Arch-Router Table 1); "from 71% accuracy to 93% accuracy" (Anthropic guide).
  • Effort: about 2 h. Build a TS classify() with a JSON schema {route, confidence, reason} and 2-3 examples per route.
  • Risks: adds one model round trip (latency). About 15% route error per Arch-Router's numbers on its benchmark.
  • Verdict: TRY FIRST as the fallback stage of B4.
  • Scores: Ev 3 · Cr 4 · Cost 5 · Rel 5 · Rec 4

TRY FIRST B4. Hybrid router (rules/embeddings first, LLM on uncertainty)
Cheap stages handle confident cases. Only uncertain messages go to the LLM classifier.
  • Sources:
  • Arora et al., "Intent Detection in the Age of LLMs" (2024-10-02, paper) https://arxiv.org/abs/2410.01627
  • UDRIL, "Efficient Out-of-Scope Detection in Dialogue Systems via Uncertainty-Driven LLM Routing" (2025-07-02, paper) https://arxiv.org/abs/2507.01541
  • Claude ticket-routing guide (undated, docs) https://docs.claude.com/en/docs/about-claude/use-case-guides/ticket-routing
  • Claims: Arora et al. route to an LLM only when a cheaper intent model is uncertain. This gets near-LLM accuracy at about half the latency. UDRIL sends only low-confidence cases to an LLM using uncertainty thresholds. Its LLM stage was fine-tuned, so take the routing idea, not the model.
  • Problems (1-8, Esc): 5, 1, 3, 8. Esc: yes.
  • Reported numbers: "within 2% of native LLM accuracy with 50% less latency" (Arora). Thresholds "τ=0.15 ... τ=0.10 ... τ=0.05" (UDRIL).
  • Effort: about 3 h on top of B1+B3: regex, then (optional) embedding, then Haiku classify, then fail-open.
  • Risks: compounding stage errors. Thresholds need held-out data.
  • Verdict: TRY FIRST It is the routing shape with the best evidence for a latency-scored build.
  • Scores: Ev 3 · Cr 4 · Cost 4 · Rel 5 · Rec 4
  • Cross-refs: B1, B2, B3, B7, K1 (sticky routing skips routing calls).

  • Problems (1-8, Esc): 5. Esc: no.

  • Effort: about 3 h.
  • Risks: our build is already Haiku-class. A cascade adds latency on hard turns, and FrugalGPT's scorer is trained.
  • Verdict: SKIP We have one cheap model, and cascades optimize model cost, not prompt bloat.

TRY FIRST B7. Fail-open and "none of the above" routing (misroute safety)
The router can answer "none / irrelevant". On error, low confidence or unknown, it loads the full or default policy set, never an empty one.
  • Sources:
  • Fin, "How Fin Scales Customer-Defined Behaviour" (2026-09-25, blog) https://fin.ai/research/how-fin-scales-customer-defined-behaviour
  • Arch-Router (2025-06-19, paper) https://arxiv.org/html/2506.16655

  • Problems (1-8, Esc): 1, 6, 2 (log the route and its confidence). Esc: yes (no route plus no tool means escalate).
  • Reported numbers: "61% of planning calls came back with an empty plan"; "84% of procedure relevance checks find nothing that applies" (Fin). OOS gains "by >5% for the Mistral-7B model" (Arora).

  • Verdict: TRY FIRST It is cheap insurance for a router.

Family C: Rule precedence and conflict resolution

SKIP C1. Role-based instruction hierarchy / chain of command
Rely on the model's built-in priority (system/developer > user > tool output) to settle conflicts.
  • Sources:
  • Wallace et al., "The Instruction Hierarchy" (2024-04-19, paper; foundational) https://arxiv.org/abs/2404.13208
  • OpenAI Model Spec, chain of command (release 2026-08-18, docs) https://github.com/openai/model_spec/blob/main/model_spec.md
  • IHEval (2025-02-12, paper) https://arxiv.org/abs/2502.08745
  • ManyIH-Bench (2026-04-10, v4 2026-09-04, paper) https://arxiv.org/abs/2604.09443
  • Claims: Labs train models to prefer higher-privilege messages, and the Model Spec defines the ordering. Benchmarks show the ordering is unreliable under real conflicts, and it gets worse as the number of tiers grows (ManyIH up to 12 levels). Wallace et al. achieved the hierarchy through training, which we can't do.
  • Problems (1-8, Esc): 7 (weakly). Esc: no.
  • Reported numbers: "the most competitive open-source model only achieves 48% accuracy in resolving such conflicts" (IHEval). "even the current frontier models perform poorly (~40% accuracy) when instruction conflict scales" (ManyIH).
  • Effort: 0 h (default behaviour).
  • Risks: there is no record of which rule won (problem 7 stays unsolved), and accuracy is around 40-48% in the conflict benchmarks.
  • Verdict: SKIP Keep business rules in the system role and patient text as data, but do not rely on built-in hierarchy for precedence (about 40-48% under conflict); use C3.
  • Scores: Ev 4 · Cr 5 · Cost 5 · Rel 3 · Rec 5

State "if X conflicts with Y, X wins" or a ranked list of rule classes in the prompt.
  • Sources:
  • Anthropic, "Claude's new constitution" (2026-01-22, blog) https://www.anthropic.com/news/claude-new-constitution
  • Control Illusion (2025-02-21, v4 2025-12-04, paper) https://arxiv.org/abs/2502.15851

  • Problems (1-8, Esc): 7 (partly), 6. Esc: no.
  • Reported numbers: none quantitative beyond benchmark sizes ("six state-of-the-art LLMs"; "500 tailor-designed system messages").
  • Effort: about 1 h. Add numbered precedence lines to the core prompt.
  • Risks: compliance is unreliable, it isn't logged, and a test can only check the output.
  • Verdict: TRY IF TIME It is cheap as a backstop, but the testable version is C3.
  • Scores: Ev 3 · Cr 4 · Cost 5 · Rel 3 · Rec 5

TRY FIRST C3. Policy as code: business rules, permissions and precedence enforced in code at the tool boundary, with a priority table and decision log (merged: Analyst A's C3 + Analyst B's K3)
Encode business rules and their precedence as code that checks proposed tool calls and replies, so the winner is decided and logged by code and the model cannot talk its way past a rule.
  • Sources:
  • ToolGuards, "Towards Enforcing Company Policy Adherence in Agentic Workflows" (paper, 2025-07-22, v2 2025-10-06, EMNLP 2025 Industry): https://arxiv.org/abs/2507.16459
  • AgentSpec, "Customizable Runtime Enforcement for Safe and Reliable LLM Agents" (paper, 2025-03-24, v3 2025-07-31): https://arxiv.org/abs/2503.18666
  • Vercel AI SDK, "Policy-Based Tool Approvals" (docs, undated, TypeScript): https://ai-sdk.dev/docs/agents/policy-tool-approvals
  • DoorDash, "Building Ask DoorDash (Part 4): A Platform for Building and Evolving Agents" (blog, 2026-07-24): https://careersatdoordash.com/blog/building-ask-doordash-part-four-a-platform-for-building_and_evolving_agents/
  • Claims: ToolGuards compiles a policy document into executable guards run before tool calls; on tau-bench airline it beat both the plain agent and reflection prompting by a wide margin in pass^k. AgentSpec gives a rule DSL (trigger, predicate, enforcement) with millisecond overhead. The AI SDK ships an OPA/Rego package for TypeScript, with rules as code that are unit-testable and enforced at the tool boundary. DoorDash says prompt guidance "is advisory. Validation and enforcement run in tool code on every call", and that permissions only in the prompt "would add context without guaranteeing enforcement". Progent (arXiv 2504.11703, opened by Analyst A) applies the same idea with symbolic privilege rules per tool call.
  • Problems (1-8, Esc): 7 (code decides and logs the winner), 2, 6, 8 (one unit test per conflict pair), 1 (whole rule classes leave the prompt). Esc: yes (a cannot_do intent list such as charge card, move paid money, hold a clinic date forces escalation; see E2).
  • Reported numbers: baseline "pass^1 rate of 0.450 and a pass^10 rate of 0.227" vs ToolGuards "0.685 and 0.500"; reflection "only very modest improvements, reaching a pass^10 of 0.273" (ToolGuards). "prevents unsafe executions in over 90% of code agent cases"; "overheads in milliseconds" (AgentSpec). DoorDash: shared MCP server with more than 60 tools.
  • Effort: about 3 h. TS rules.ts array of {id, priority, when(ctx), effect}, a resolver that sorts matches by priority, applies the top one and logs {turn, matched:[ids], winner:id}; wrap each of the 14 tools with checks (allowed for this route, required args present, price comes from clinic data); cannot_do intents force escalate=true. Plain TS, not OPA, for a 10-hour build.
  • Risks: Only rules expressible over structured state (tool args, route, flags) can be coded; tone and wording rules stay in the prompt. Overlaps D (validators) and E (handoff); build them as one module.

TRY FIRST I1. Stable-prefix / dynamic-suffix prompt caching (merged: Analyst A's A5 + Analyst B's I1)
Put everything that never changes (core rules, all tool definitions) first, mark a cache breakpoint at its end, and keep per-message content after it, so repeat turns pay about 10% of the input price for the prefix.
  • Sources:
  • Anthropic, "Prompt caching" (docs, undated living page, opened 2026-10-11): https://platform.claude.com/docs/en/build-with-claude/prompt-caching
  • Anthropic, "Prompt caching with Claude" (announcement; page dated 2025-08-14, carries a 2024-12-17 GA note, so the original is 2024): https://claude.com/resources/articles/prompt-caching
  • TikTok for Developers, "TikTok saves up to 50% on costs with ~50 lines of code with Prompt Caching" (blog, 2025-09-06): https://developers.tiktok.com/blog/tiktok-saves-50-percent-with-prompt-caching
  • OpenAI, "Prompt caching" (docs, living page, opened 2026-10-11): https://developers.openai.com/api/docs/guides/prompt-caching
  • Claims: Anthropic caches the prompt prefix up to a cache_control breakpoint; a cache write costs 1.25x base input (5-minute TTL) or 2x (1-hour TTL) and a read costs 0.1x, with at most 4 breakpoints and a 20-block lookback. The launch post reports large latency and cost cuts on long prompts, including a "10-turn convo with a long system prompt" case. TikTok's internal QA agent cut daily cost about 40-50% after adding caching because input tokens were about 78% of its cost. Manus (see I2) adds that agent workloads are dominated by input tokens (about 100:1) and that anything changing early in the prompt, such as a timestamp, destroys the cache. OpenAI caches prefixes of 1,024+ tokens automatically and recommends a stable prompt_cache_key.
  • Problems (1-8, Esc): 5 directly; indirectly 1 (lowers the cost of whatever stays always-on). Does nothing for quality. Esc: no.
  • Reported numbers: up to 90% cost and 85% latency reduction for long prompts; 10-turn conversation with a long system prompt about 10s to about 2.5s (-75%), cost -53%. Cache read 0.1x, 5-min write 1.25x, 1-h write 2x. Haiku 3.5 row: $0.80 base input, $1 5m write, $1.60 1h write, $0.08 hit per MTok. Minimum cacheable prompt: 4,096 tokens for Claude Haiku 4.5, 2,048 for Haiku 3.5, 512 for Haiku 5.5 (re-verified by the supervisor on the docs page, 2026-10-11). TikTok about 40-50% daily savings. OpenAI cached input "discounted up to 95%", 1,024-token minimum. Manus: Sonnet cached $0.30/MTok vs uncached $3/MTok, "a 10x difference".

Split the TS system prompt into a system array with cache_control: {type: "ephemeral"} on the last static block (core + all 14 tool schemas), log cache_creation_input_tokens and cache_read_input_tokens per turn, rerun the suite for cost and latency. Also run a "monolith + caching" variant as a second baseline.

A burst-run 65-case suite overstates hit rates versus real SMS gaps beyond 5 minutes (report 1-h TTL too). Writes cost extra, so a rarely reused prefix costs more than no caching. Variable modules placed before the breakpoint kill reuse (I2).
  • Verdict: TRY FIRST Cheapest lever on problem 5, no architecture change, and the cost baseline every other method must beat.
  • Scores: Ev 4 · Cr 5 · Cost 5 · Rel 5 · Rec 4

Anything that changes per message (which skills were loaded, working memory, the current time, patient record) goes after the cached prefix as a trailing message, never in the middle of the system prompt.
  • Sources:
  • ProjectDiscovery, "How We Cut LLM Costs by 59% With Prompt Caching" (engineering blog, 2026-04-10): https://projectdiscovery.io/blog/how-we-cut-llm-cost-with-prompt-caching
  • Anthropic (claude.dev), "Lessons from building Claude Code: Prompt caching is everything" (engineering blog, 2026-04-30): https://claude.dev/blog/lessons-from-building-claude-code-prompt-caching-is-everything/

Claude Code: "A few percentage points of cache miss rate can dramatically affect cost and latency" (no figure).

Treat the number of simultaneous rules as a capacity limit, keep only the handful each message needs, and expect a Haiku-class model to drop rules (omission), not bend them, when overloaded.

TRY FIRST I5. Focused context over full context (evidence base for "shorter prompt, better reply")
The same task with only the relevant text beats the same task with everything included, even well inside the context window and even when retrieval is perfect.
  • Sources:
  • Chroma, "Context Rot: How Increasing Input Tokens Impacts LLM Performance" (technical report, 2025-07-14): https://www.trychroma.com/research/context-rot
  • Levy, Jacoby, Goldberg, "Same Task, More Tokens" (paper, 2024-02-19): https://arxiv.org/abs/2402.14848
  • Du et al., "Context Length Alone Hurts LLM Performance Despite Perfect Retrieval" (paper, 2025-10-06): https://arxiv.org/abs/2510.05381
  • Modarressi et al., "NoLiMa: Long-Context Evaluation Beyond Literal Matching" (paper, 2025-02-07): https://arxiv.org/abs/2502.05167
  • Claims: Chroma tested 18 LLMs (GPT-4.1, Claude 4, Gemini 2.5, Qwen3). Performance varies with input length even on simple tasks. On LongMemEval, focused prompts of about 300 tokens scored significantly higher than full prompts of about 113k tokens for every model. Levy et al. hold the task fixed, pad the input, and see reasoning drop by 3,000 tokens. Du et al. show degradation even when the irrelevant tokens are whitespace or masked, and when the evidence sits right before the question. NoLiMa shows that when the question and the needle share few words (as with a paraphrased SMS vs a policy rule), most models fall below half their short-context score by 32K. LIFBench (ACL 2025) adds that instruction following specifically declines with length, especially beyond 16k-32k tokens (https://aclanthology.org/2025.acl-long.803/, 2025-07-11).
  • Problems (1-8, Esc): 1 (core evidence), 5 (shorter prompt also costs less).
  • Reported numbers: Chroma 18 LLMs, 194,480 calls, focused ~300 tokens vs full ~113k tokens. Levy et al. average accuracy 0.92 to 0.68 at 3,000 tokens. Du et al. degradation of 13.9%-85% as input length grows, within claimed lengths; recitation mitigation gives GPT-4o up to 4% on RULER. NoLiMa: at 32K, 11 of 13 models drop below 50% of their short-context baselines; GPT-4o 99.3% to 69.7%. LIFBench: 2,766 instructions, 20 LLMs, six length intervals.
  • Effort: 0 h extra. This is the hypothesis the eval tests. Report quality per prompt-size bucket (monolith 25k vs routed) on the 65-message suite.

2. Direct answers to the "Questions:" lines

A. Model-picks vs code-picks the skills, failure modes of each, reported token savings, how people keep skills from conflicting

Model-picks vs code-picks. Every head-to-head we found favors code-picked or always-present rules over model-triggered skills: Vercel saw the skill never invoked in 56% of cases while an always-on compressed index reached 100% (A3); Skills in the Wild had forced loading at 55.4% vs agent-decided 51.2% (A2); LangChain got invocation to only 70% even with a prompt telling the model to use skills (A1). For a Haiku-class SMS bot, code should choose the modules and the model should only see what was chosen (A2, K2), behind a small always-on core (A3).

Failure modes. Model-picked: never invoked, wrong skill loaded silently, an extra round trip per load (A1). Code-picked: a misroute loads the wrong modules, so it needs an explicit "none" class and fail-open to the full set (B7), plus the router's own test cases (G5).

Reported token savings. "Up to 81.7%" of eager-loading tokens at a 15% latency cost (Workday, A1); "85% reduction" with Tool Search on 58-tool libraries (I3); Vercel's index cut 40KB to 8KB at a 100% pass rate (A3); Anthropic removed "over 80%" of Claude Code's system prompt with no measurable loss (A3); DoorDash's skill scoping cut instruction tokens 50-60% per turn (K1); skills on one agent used 53.7% fewer tokens than a multi-agent pipeline (J2).

Avoiding conflicts. Keep the per-turn module count small (SkillsBench gains peak at 2-3 skills and fall at 4 or more, A7), keep modules compact and human-written (A7), make routing descriptions distinct because selection collapses when descriptions are confusable (J2, K2), scope by product tag (K4), and move skill-vs-skill precedence into a code resolver (C3). Nobody we found resolves conflicts reliably inside the model (C1, C2).

B. How misroutes are detected and recovered, latency of each router type, whether a hybrid (rules first, classifier fallback) is common

Detection and recovery. The standard tools are an explicit "none / irrelevant" class (Arch-Router's Irrelevance category, out-of-scope detection in Arora et al.; B7), confidence thresholds that push uncertain cases to a stronger stage (UDRIL; B4), fail-open to the full or default set on error or timeout (Fin; B7), and an out-of-scope hand-back from a pinned domain that triggers a reroute within the same turn (DoorDash; K1). Downstream validators (D1) and escalation triggers (E2) catch what slips through, and logging route plus confidence per turn makes misroutes diagnosable (F1). Misroute fixes in practice are edits to the routing description with key terms and example phrasings (Agentforce; K2).

Latency. Rules: effectively zero (no figure published; B1). Embedding classifiers ran "14 and 81 times faster" than prompting on Thumbtack data (B2). Hybrid LLM fallback came "within 2% of native LLM accuracy with 50% less latency" (B4). A trained 1.5B router was "over 28 times faster than its closest competitor" (B6, skipped). A prompted Haiku classify call adds one model round trip; no source gave a millisecond figure for our setup, so measure it on the suite (B3).

Is hybrid common? Yes among the sources opened: Arora et al. and UDRIL route to an LLM only on uncertainty, Intercom/Fin layer deterministic rules over model decisions, Anthropic's ticket-routing guide combines classification with retrieved examples, and DoorDash pins follow-ups to skip routing calls (B4, K1). There is no survey-level adoption figure.

C. How do people encode "rule X overrides rule Y" so it is testable, and how do they log which rule won

Encoding. Testable precedence lives in code: policy compiled into guard functions (ToolGuards), a trigger-predicate-enforcement DSL (AgentSpec), OPA/Rego policies in the TypeScript AI SDK, and DoorDash's "enforcement runs in tool code on every call" (all C3). Prompt-level orderings are unreliable: 48% (IHEval) and about 40% (ManyIH) conflict-resolution accuracy (C1), stated priorities overridden by model biases (C2, Control Illusion), and system obedience called "fragile" in mechanistic work (F9). For us: a rules.ts table with numeric priority, a resolver, and one unit test per conflict pair (C3), with a numbered precedence list in the prompt only as a backstop (C2).

Logging the winner. Fin cites the guideline ID and a reason category for every escalation decision (C4). Log per turn {loaded_modules (A2), route + confidence (B4), matched_rules + winner (C3), model_applied_rules (C4), validator_failures (D1), escalate (E1)} using OTel GenAI attribute names (F1). Treat the model's self-cited IDs as a hint and the code-side record as ground truth; for "which module caused this failing reply", rerun the case with each loaded module removed (F7).

D. Retry budgets people use, whether deterministic validators + one retry is a known pattern, any numbers

Budgets. instructor's documented example is max_retries=2 = "at most three SDK calls"; 12-factor agents uses about 3 attempts (consecutive_errors < 3) before escalating; Self-Refine caps at 4 iterations with most gains in the first; Anthropic's skills best-practices script uses MAX_RETRIES = 3 (D1). Under SMS latency scoring, one re-ask plus a deterministic fallback or escalation is the defensible budget (D1, E2).

Known pattern? Yes: validate, re-ask with the specific error, cap, then fall back. It is built into instructor and Guardrails AI (REASK, FIX_REASK, num_reasks) (D1). The research supports it when the feedback is external: self-correction without reliable external feedback often fails (Huang et al., Kamoi et al.; D1, D5), while code guards beat reflection (ToolGuards pass^10 0.500 vs 0.273; C3), and MAST found adding a verification step gave +15.6% (J6). Fix format problems in code with no retry at all (D2), and check every price, URL and "done" claim against this turn's tool output (D3). Keep control fields typed and validated outside prompt text (H2).

Numbers. ToolGuards pass^1 0.450 to 0.685, pass^10 0.227 to 0.500 (C3); DVR "doubles" and "triples" constraint adherence with tool feedback (D1); NVIDIA's first rail layer adds about half a second while lifting detection from 75% to 83% (D4); NabaOS receipts catch 94.2% of fabricated tool references at under 15 ms (D3).

E. Precision vs recall tradeoffs for handoff, how they detect "no tool can do this", what the handoff message looks like, how they avoid the bot pretending it handed off

Precision vs recall. Vendors tune thresholds explicitly and add hard guards (Fin: no double offer, no first-message escalation unless allowed; Intercom offers "offer" vs "escalate immediately"; Cleanlab shows lower trust thresholds escalate more and cut more failures) (B1, E3, E5). For our tests, take recall on hard triggers in code (E2) and precision elsewhere by not escalating on soft signals (E5 skipped). Use balanced should-escalate and near-miss should-not-escalate test pairs (G2, G5).

Detecting "no tool can do this". tau-bench leaves it to policy text and model judgment (E1). In a code-routed design it is structural: an explicit cannot_do intent list (charge a card, move paid money, contact a clinic to hold a date) enforced in code (C3), router label none with no mapped tool, or the same intent unresolved twice (E2). OpenAI's guide lists high-risk actions and failure thresholds as human-oversight triggers (J1). No published accuracy for capability-gap detection alone.

Handoff message. tau2-bench prescribes the order: call transfer_to_human_agents first, then send a fixed sentence; tau-bench's tool requires a summary (E1). Intercom lets admins set the handover wording and Ada defines a fallback if the transfer fails (E3). For SMS: one fixed, code-emitted sentence sent only after the escalation tool succeeds (E1).

Avoiding pretend handoffs. False success accounts for 45-48% of failures in tau2-bench single-control domains and LLM judges do not exceed AUROC 0.65 at detecting it, while cheap lexical detectors recover 4-8x more at 3,300x lower latency (E4, D6). The fix is a receipt check in code: handoff language with no executed escalate_to_human call this turn is blocked or converted into a real call, and only code ever emits the handoff sentence (E1, E4, D3).

F. Is there a standard trace shape for "which instructions were loaded, which tools ran, which checks failed"; anything beyond logging

Partly. Tools and checks have standard slots: OTel GenAI execute_tool spans and the gen_ai.evaluation.result event (F1), OpenInference TOOL / GUARDRAIL / EVALUATOR span kinds (F3), and Braintrust tool / score / classifier spans (F4). "Which instructions were loaded" has no standard field beyond the opt-in gen_ai.system_instructions; the practical answers are prompt-version linking (Langfuse F2; OpenInference llm.prompt_template.version F3) or custom attributes such as app.skills.loaded, app.rules.fired, app.validators.failed (F1). The OTel GenAI spec is still "Development" and moved repos in June 2026, so pin a version. Beyond logging, published attribution methods (ContextCite, AT2, AttriBoT, TracLLM, AttnTrace, JoPA) need token likelihoods, attention or open weights and do not run on hosted Haiku (F7-F9). The usable step is black-box leave-one-module-out replay of failing cases (F7), which only works once the policy is modular.

G. Smallest credible eval for ~65 cases; how to mix deterministic checks with a judge; how to derive test cases from a policy document

Smallest credible eval. 65 deterministic cases already exceeds Anthropic's "20-50 tasks from real failures" starting point (G2) and Hamel Husain's 20-50 outputs per review (G4). Credibility comes from how it is run: at least 3 repetitions per method with pass^3 next to the mean (G3), per-check results, balanced should/should-not escalate cases (G2), and a confidence interval (at 60/65 the 95% Wilson interval is about 83-97%, our arithmetic; G3). Run it in promptfoo with JS assertions and --repeat 3 (G1). Give the monolith baseline the same prompt-polish budget as the routed build, since a single prompt tweak moved Anthropic's research agent from 30% to 80% (J5, H1).

Mixing checks and a judge. Deterministic checks first; a judge only where no rule can decide (G2, G4). Every criterion in the brief's suite is code-checkable, so the headline score should be all code. If a tone or pacing judge is added, make it binary with an explanation, from a different model family than Haiku (self-preference), with reference answers (MT-Bench reference-guided math failures fell from 14/20 to 3/20), validated by TPR/TNR on 20-30 hand labels and reported separately (G6). Do not use a judge in-line as a validator (D6). Grade outcomes, not exact tool-call sequences (G2).

Deriving cases from the policy. A CheckList row per policy module with a minimum-functionality test, an invariance test (paraphrases, such as five ways to ask for a person) and a directional or near-miss test (G5), seeded from error analysis of the monolith's real failures (G4). PromptPex automates spec extraction and test generation; tau2-bench composes atomic scenarios (country x financing x escalation) (G5). Tag each case with its module for problems 2 and 8.

H. Is prompt optimization realistic in a 10-hour budget; what is the minimum viable version

Realistic? Technically feasible, a poor bet inside 10 h. GEPA needs about 100-500 evaluations and Databricks reports 2-3 h runs (H3, H5), but integration takes 3-5 h (Python GEPA or adopting Ax, H4), it needs a frontier reflection model (Decagon: GPT-4o-mini left the prompt unchanged), prompts grow unless capped (Databricks, Decagon), gains on instruction following are modest (IFBench 47.79 to 52.72 on GPT-4.1 Mini) and one variant regressed (28.23 vs 36.90) (H3). Optimizing on the judged 65 also invalidates the comparison unless cases are held out. A practitioner reports 3 days of automated hill-climbing with no gain vs real progress from a couple of hours of manual rewriting (H1).

Minimum viable version. (1) Keep control out of prompt text: router and reply output as typed, validated JSON with escalation as a field (H2). (2) Make each deterministic check return a reason string ("invented price $X not in tool result"). (3) Manual loop per module: run suite, read failures by module, rewrite, rerun, keep or revert (H1). (4) Only with 3+ h left: length-capped GEPA (Python or AxGEPA) on one module with a Sonnet-class reflector, about 150 metric calls and a held-out split (H3, H4, H5).

I. Numbers we can cite for "shorter prompt, better reply"; caching patterns that keep the dynamic part small

Shorter prompt, better reply. Instruction count: claude-3.5-haiku follows 98.0% of 10 simultaneous instructions, 78.0% of 50 and 43.4% of 100, mostly by omission (IFScale; I4). Real agent prompts: instruction success nearly 0 above 6,000 words for every model, and the 25k-token monolith is far past that (AgentIF; I4). Domain distractors: niche rules forgotten as domains are added and single agents falling off at 2+ unrelated domains (LangChain; I4, J4). Length alone: focused ~300-token prompts beat full ~113k-token prompts for all 18 models (Chroma), 0.92 to 0.68 accuracy at 3,000 tokens (Levy et al.), 13.9%-85% degradation even with perfect retrieval (Du et al.), 11 of 13 models below half their baseline at 32K (NoLiMa) (I5). Trimmed prompts losing nothing: over 80% of Claude Code's system prompt removed with no measurable loss (A3). Production: DoorDash cut instruction tokens 50-60% per turn with skills but published no quality delta for that change (K1). None of these is a 25k-token SMS policy bot, so our own suite is the number that counts.

Caching patterns. Core rules plus all tool schemas first with one cache_control breakpoint (I1); history next; per-turn skill text, patient context and a date-only stamp in a trailing message after the breakpoint (I2); a fixed tool list and no mid-thread model switch (I3). ProjectDiscovery's relocation of a per-message "Relevant Skills" block took its hit rate from under 8% to about 74%, then 84% (I2). Two traps: the routed static prefix must stay above the model's minimum cacheable length (4,096 tokens on Claude Haiku 4.5; 512 on Haiku 5.5), and SMS gaps often exceed the 5-minute TTL (I1).

J. For a reply-drafting bot, is a sub-agent for side tasks worth the latency, and what do people report

Not on the reply path; yes as an isolated tool for genuine side tasks. Every primary source starts with one agent plus code routing (J1). Skills on one agent matched multi-agent accuracy with 53.7% fewer tokens and 49.5% lower latency (J2). Anthropic's multi-agent system uses about 15x chat tokens and is scoped to breadth-first research (J5), and budget-matched studies find single agents match or beat multi-agent designs (J6). Package lookup is a deterministic tool call. Call summary fits a narrow summarizer that returns facts, precomputed when the call ends and stored on the patient record so the SMS turn pays nothing extra (J3). Reported cost: one extra model call per interaction for the subagent pattern (4 vs 3 on a one-shot request, LangChain; J2). Nobody published a support-bot latency figure for a summary sub-agent.

K. The standard way to add a second domain without touching the first

A convergent pattern, not a formal standard: a shared core (escalation, tone, tools, tracing, eval harness), domain-owned modules each carrying their own instructions, skills, tool allowlist and eval cases, a router that sees only short per-module routing descriptions, and follow-up turns pinned to the active domain with an out-of-scope hand-back (K1, K2). DoorDash added its third domain in one week on this setup, "roughly 10x faster" (K1). Agentforce and Copilot Studio formalize the per-module manifest (K2); Intercom and Zendesk tag content by product or brand, but default untagged content to deny, not "Everyone" (K4). Two guardrails make "without touching the first" real: every domain's regression cases run on every shared change (K1), and business rules live in each domain's tool code (C3). Minimal version for 10 h: core/ plus products/hair/ (later products/fertility/), a product tag on the patient record, and no LLM-to-LLM handoffs yet (J4 deferred to domain 2).

3. Ranked shortlist for the 10-hour budget

One standard for both halves: one TypeScript developer, about 10 h, hosted Haiku-class model, no fine-tuning, judged on ~65 deterministic cases plus token cost and latency against the monolith. The card estimates for items 1-7 add up to roughly 14-15 h because the analysts sized each card on its own. The hours below are compressed estimates that assume shared code (one trace object, one reply schema, one validator module). If you fall behind, cut from the bottom of the list.

  1. Eval harness first (G1 + G3 + G2), about 2 h. Port the 65 cases to promptfoo with JS assertions (required facts, escalation flag, URL placement, no invented prices, cost, latency), run each case 3+ times, report pass^3, per-check results and a Wilson interval, and log cache read/write tokens and modules loaded per turn (F1 attribute names), because one run of 65 cases cannot separate methods.
  2. Baseline error analysis and a fair monolith (G4 + H1), about 0.5-1 h. Read the monolith's failures, tag each with the policy module it belongs to (this becomes the module map), and give the monolith the same polish budget and the same caching (I1) as the routed build, since one prompt tweak moved Anthropic's agent from 30% to 80% (J5).
  3. Small always-on core plus code-picked modules (A3 + A2 + A7 + K2, K1-lite), about 2 h. Distill a 1-2k-token core (identity, SMS style, escalation rule, never invent prices) and load at most 3 policy modules per turn chosen by code from skills/*.md with front-matter {id, route_description, products, tools} under core/ and products/hair/, never letting Haiku decide whether a policy applies (Vercel: skill never invoked in 56% of cases; LangChain: 70% invocation even when prompted).
  4. Hybrid router with fail-open (B1 + B3 + B7, part of B4), about 1.5 h. A regex pre-router handles "talk to a person" and ack-only messages like "ok thanks" with no model call, one structured Haiku classify call over the route descriptions handles the rest, and errors, low confidence or "none" fall back to the full module set, with route and confidence logged.
  5. Code-owned escalation with a receipt check (E1 + E2 + E4, using C3's cannot_do list), about 1.5 h. Escalation is an escalate_to_human({reason, summary}) tool executed by code, forced by code triggers (explicit request, impossible actions such as charging a card, moving paid money or holding a clinic date, route "none", retry budget spent), with the one-sentence handoff emitted only by code after the tool succeeds and any handoff wording without a tool call blocked (false success is 45-48% of failures in tau2-bench single-control domains).
  6. Grounding validators, code repair, one retry, typed output (D3 + D2 + D1 + H2 + C4), about 2 h. The reply is typed JSON {reply, escalate, urls[], applied_rules[]}; code checks every price, URL and ID against this turn's tool output, fixes format problems in code, re-asks once with the specific error, then falls back or escalates.
  7. Cache layout with a size check (I1 + I2), about 0.5 h. Core plus all 14 tool schemas form one cached prefix and loaded skill text plus patient context go in the uncached tail. Check that the prefix stays above the model's minimum cacheable length (4,096 tokens on Claude Haiku 4.5, 512 on Haiku 5.5). If it doesn't, either keep stable material (tool schemas, fixed examples) in the prefix to clear the minimum or accept and report that a cached monolith may be cheaper per turn.

About 10 h ends here.

  1. Priority-table resolver and decision log (C3 full), about 1.5 h. rules.ts with numeric priority, a resolver that logs {matched, winner}, and one unit test per conflict pair (problems 7 and 2), because prompt-level precedence resolves conflicts only about 40-48% of the time (C1).
  2. Rules-per-turn metric (I4), about 0.5 h. Count the rules loaded per turn for the monolith vs the routed build and report it next to pass rate, which makes the "load less" case measurable.
  3. Call-summary sub-call (J3), about 1.5 h. Give problem 4 a home as a precomputed summarizer tool, not a sub-agent on the reply path.
  4. Leave-one-module-out replay (F7), about 2 h. Use it when a failing case can't be explained from the trace.
  5. Only with 3+ h left: length-capped GEPA on one module with a held-out split (H3/H4/H5), embedding router stage (B2), product/country tags (K4), a calibrated tone judge (G6), tool masking (I3), Langfuse prompt-version linking (F2).

How the tensions are reconciled: - Load less vs keep the cache. Load less text through the tail, not the prefix. The prefix stays stable and above the model's cache minimum, and the eval measures routed+cached against monolith+cached on both cost and quality (I1, I2, A3). - Skills vs reliability. Use the skill file format (A1, K2) for packaging and testing, but code does the selection (A2), capped at 3 modules per turn (A7), with confusable descriptions checked (J2). - Precedence. Code (C3) decides precedence. The prompt ordering (C2) is only a backstop, and self-cited rule IDs (C4) are hints. - Handoffs. Escalation state is a tool receipt, not prose (E1, E4, H2). - Measurement. Every method is compared on 3+ runs with intervals (G3), and the monolith gets equal polish and caching (H1, I1).

4. Surprises

Merged and deduped from both analyses. Items 1-6 contradict or change the plan implied by the brief (routing + skills + validators). Items 7-10 are methods the brief didn't list that fit better. Items 11-16 are measurement and tooling cautions.

Contradictions and corrections to the plan

  1. Model-triggered skills are the weakest part of the plan. Three independent 2026 sources found that models often don't invoke the right skill. Vercel saw the skill never invoked in 56% of cases, and an always-on index scored 100% (A3). LangChain reached only 70% invocation even with prompting (A1). Skills in the Wild had forced loading beat agent-decided loading, 55.4% vs 51.2% (A2). Keep the modular file format, but pick modules in code behind a small always-on core.
  2. Routing can switch caching off. On Claude Haiku 4.5 the minimum cacheable prompt is 4,096 tokens (verified on Anthropic's docs; it is 512 on Haiku 5.5). If routing shrinks the static prefix below that, nothing is cached. A cached 25k monolith paying 0.1x could then cost less per turn than an uncached routed prompt (I1). Skill text placed inside the system prompt also breaks caching. ProjectDiscovery's per-message "Relevant Skills" block held its hit rate under 8% until it was moved to the tail (I2). The plan needs to say where loaded text goes and which model ID is used.
  3. Precedence belongs in code, not in the prompt. Prompt-level hierarchies resolve conflicts only about 40-48% of the time (IHEval, ManyIH; C1). Stated priorities get overridden by model biases (C2), and mechanistic work calls system obedience "fragile" (F9). Code guards beat reflection on tau-bench, pass^10 0.500 vs 0.273 (C3). The plan's "rule precedence" item should be a resolver plus a decision log.
  4. More modules can recreate the monolith. SkillsBench's gains drop from +19.0 pp at 2-3 skills to +10.1 pp at 4 or more. Comprehensive docs-style skills add only +0.7 pp, and self-generated skills are negative (A7). Skill selection collapses past a library size driven by how confusable the descriptions are (J2). Financing, payment and insurance-by-country modules are likely to be confusable, so cap modules per turn at 3, test near-miss routes, and consider a two-level product-to-skill hierarchy.
  5. A trimmed prompt may lose nothing. Anthropic removed "over 80%" of Claude Code's system prompt with no measurable loss, and Vercel compressed its index 80% at a 100% pass rate (A3). Distilling the monolith could be a cheap, large win before any routing, so test "distilled monolith" as its own variant. Caveat: these are frontier models on coding evals.
  6. Multi-agent is not the upgrade path. Skills on one agent matched multi-agent accuracy with 53.7% fewer tokens and 49.5% lower latency (J2). Budget-matched studies find single agents match or beat multi-agent designs (J6), and Anthropic's multi-agent system uses about 15x chat tokens (J5). Routing + skills is supported. "Add sub-agents" is not.

Unlisted methods that fit better

  1. Pre-send receipt checks against false success. The biggest handoff risk in recent data is the bot claiming something it didn't do. That accounts for 45-48% of failures in tau2-bench single-control domains, and LLM judges top out at AUROC 0.65 at detecting it (E4, D6). A deterministic check that compares claims to actual tool calls (E4, D3) protects both the escalation flag and the no-invented-prices test.
  2. Rules enforced in tool code. DoorDash, Agentforce and OpenAI all treat prompt rules as advisory and enforce in tool code (C3, merged K3). For escalation in particular, a code-level cannot_do list beats any prompt rule.
  3. Control-data flow separation. Free-text prompt optimization broke routing protocols (naive TextGrad: 0.0% stability on MARG). Keeping control as typed, validated objects gave 100% eventual protocol validity (H2). Escalation and route should be validated fields, never prose rules.
  4. Fail-open is the norm, and most turns need little. Fin found 61% of planning calls returned an empty plan and 84% of procedure checks found nothing that applied (B7, A2). Defaulting to "load less" is safe if failures fall back to more. Fin also moved escalation and selection off the main LLM into separate classifiers. Theirs are fine-tuned, but a code trigger or a separate cheap classify call is the prompted analogue (E3, E2).

Measurement and tooling cautions

  1. One run of 65 cases is too noisy to rank methods. At 60/65 the 95% Wilson interval is about 83-97% (our arithmetic). IBM saw 77.4% mean vs 53.0% all-5-pass (G3). Run 3+ reps.
  2. The baseline needs equal polish. A single prompt tweak moved Anthropic's research agent from 30% to 80% (J5), so early prompt fixes can swamp architecture effects (H1).
  3. A Haiku-class model fails by omission. claude-3.5-haiku drops instructions outright, with an omission:modification ratio above 20-30 (IFScale; I4). That argues for deterministic presence checks over judge-style quality checks.
  4. No attribution method works on hosted Haiku as published (F7-F9). "Which rule caused this reply" is answered by architecture: modular skills, a trace manifest and leave-one-module-out replay. A monolith cannot be ablated at rule level on this budget.
  5. Prompt optimizers bloat prompts and need a frontier reflector. Databricks attributes higher serving cost to longer GEPA prompts. Decagon saw 5,000+ characters unconstrained, and GPT-4o-mini as reflector changed nothing. GEPA+Merge regressed to 28.23 vs 36.90 on IFBench with Qwen3-8B (H3, H5).
  6. Tooling churn. Anthropic warns that checking exact tool-call sequences is too rigid, so treat route correctness as a diagnostic and not a gate (G2). OTel GenAI conventions moved repos in June 2026 and remain "Development" (F1). Promptfoo agreed to be acquired by OpenAI on 2026-03-09, and both say the open-source CLI continues (G1).

Methods note

  • Process. The supervisor wrote the brief and split it into families A-E (Analyst A, Workers 1-2) and F-K (Analyst B, Workers 3-4). The analysts wrote X search queries per worker. Workers ran them, followed links, and also searched the web, arXiv, official docs and GitHub directly for every named item, logging everything to JSONL. The analysts deduped, opened and verified each source, scored methods on the protocol rubric (evidence, credibility, cost-to-test, relevance, recency) and wrote analysis-A.md (30 cards) and analysis-B.md (52 cards). The supervisor merged them into this report.
  • Raw items. 1,261 worker records: worker-1 583, worker-2 516, worker-3 99, worker-4 63. Of these, 1,052 are X posts and 209 are web or primary-source records. Analyst A also logged 81 directly opened sources (raw/analyst-a-direct.jsonl), and Analyst B reports 129 unique source URLs opened and checked on 2026-10-11. The two analyses together cite 207 unique URLs. X was used for discovery only; no card rests on an X post alone, and X-only figures are excluded from the numbers table.
